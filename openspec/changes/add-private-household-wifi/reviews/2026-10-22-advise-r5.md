## Blind take (written before opening design.md or tasks.md)

Sources: proposal.md, `specs/private-household-wifi/spec.md`, the living
`wifi-internet-uplink`, `node-connection-profiles`, and `identity-derived-ula`
specs, the household-network-management requirement, and the cited code
(`model.rs:34`, `uplink.rs:227`/`:261`, `roam.rs:33`/`:122`, `alloc.rs:34`).

1. Pin: submission is typed against an adapter that snapshots and restores the secret file, like `ProvesUpstream`. `OpenWrtAdapter` only hashes the four UCI files, so it would lose the secret on restore.
2. Pin: `wpa_psk_file` works with `psk2` and no `key`, but not with SAE. The file line shape and the passphrase charset must be pinned so a newline cannot add a second PSK line.
3. Pin: "IPv6 not enabled" read from UCI does not mean the guest link has no IPv6. Linux gives every interface an `fe80::` address. dropbear, uhttpd, and dnsmasq listen on `::` by default. A CIDR-keyed IPv4 INPUT reject does not cover that.
4. Pin: `Plan` is one `node_id`. The fleet INPUT reject is checked on other nodes' configs at build time. Between that build and N's commit, a peer's revision can drop the class while N's SSID is not yet committed. Name what orders these steps.
5. Pin: the deny aggregates are written as `10.42.0.0/16`, but the mesh space is a default (`alloc.rs:34`). A guest CIDR outside the denied aggregate would make another node's guests count as "internet".
6. Pin: `guest_routes` (`roam.rs:122`) admits any mesh-space neighbour outside `own_subnet`, so a guest lease would get a proto-158 `/32` unless it is excluded.
7. Refuse: a guest profile on a house with UCI IPv6 on. Stock `ula_prefix` stays on the fleet (`identity-derived-ula`; fixture `node_profile.rs:1541`), so guest is refused everywhere today. That is honest, but the design should say it.
8. Refuse: any guest `/32` export, any `br-lan` bridge, and an "isolated" label that only the UI adds.
9. Tradeoff: refusing IPv6 instead of building a v6 deny is less work and leaves no gap, but it makes guest a feature nobody can turn on until IPv6 is stripped or a later v6 deny lands.
10. Concern: a mixed cutover (some nodes `psk2`, some still open under the same SSID) breaks saved-network roaming. That belongs to `lpv`, but it should be named.

## Steelman

The design is careful, and most of my take is already in it. The secret
path follows the uplink precedent exactly. The isolation gate uses
aggregates, not peer lists. The class lives in committed config, not in
a fleet object nobody applies. Joiners are excluded until they carry the
class. Refusing IPv6 instead of half-building a v6 deny is the
conservative choice, and I would make it too. Rendering nftables is
correctly not owed. The plan only has to *state* the denies.

The strongest defence against R5-1 is that the refusal predicate was
meant to make IPv6 moot. It does not. The predicate reads UCI, and the
kernel does not consult UCI before it assigns `fe80::/64` to the guest
interface. The defence against R5-2 is that one owner applies through one
transaction at a time, so a concurrent peer drop is unlikely. That is
true, and it is why R5-2 asks for one sentence, not a redesign.

## Send-back items

### R5-1 — Same-node isolation over IPv6 link-local (blocking)

The INPUT reject is keyed on the guest-source class, which is a set of
IPv4 CIDRs. A guest on node N can reach `fe80::<N>%guest` on any port N
listens on with `::` (dropbear 22, uhttpd 80/443, and any v6 listener
that is added later). The IPv6 predicate is false on such a node, so
nothing refuses the plan. The spec's guest-to-resident deny ("every house
node rejects INPUT from the committed guest-source class except DHCP and
DNS") does not hold on the guest's own node.

Owed: the plan states one of these, and a test pins it:
- the guest interface's device carries `ipv6 '0'` (no IPv6 on the guest
  link at all), or
- the guest-serving node's INPUT reject is keyed on the guest interface for
  both families, with only DHCP and DNS (v4) accepted.

Either one is a sentence in the spec and design plus one builder assertion.
The first is simpler and matches the refusal posture.

### R5-2 — Name what orders the cross-node steps (blocking, wording only)

`Plan` CASes only N's revision. The gate reads every peer's committed
config at build time. The drop-guard on peer B fires only once N's guest
SSID is *committed*. If B drops N's CIDR between N's build and N's commit,
both transactions pass. The exposed surface is B's non-aggregate addresses
(gateway WAN, `wwan`, recovery `192.168.1.1`), because N's forward deny
still covers the aggregates.

Owed: one sentence in design.md that names what orders these steps. For
example: the guest-enable submitter re-reads every peer revision it built
against right before it submits N and refuses if any moved, *or* one
house-level apply session runs at a time. Also name the residual window
that is left. No new mechanism is required.

### R5-3 — Deny aggregate is the mesh space, and the guest CIDR is inside it (blocking)

The destination deny is written as `10.42.0.0/16`, but `DEFAULT_MESH_SPACE`
is a default. Nothing requires the guest `/subnets/{cidr}` to sit inside
the denied aggregate. A guest CIDR outside it would let N's guests reach
M's guests as "a destination outside those aggregates that is not a house
node address". That breaks the proposal's "cross-node guest reachability"
deny.

Owed: the deny aggregate is the committed mesh client space (default
`10.42.0.0/16`) plus `10.254.0.0/16`, and the builder refuses a guest CIDR
outside the client space. Add a test with a guest CIDR outside the space.

## Notes (not blocking)

- State in design.md that on today's fleet the IPv6 predicate is true
  (stock `ula_prefix`, `wan6`), so every guest plan is refused until IPv6
  is stripped or a v6 deny lands. Add a test against the existing
  `node_profile.rs` fixture.
- Guest-to-guest on the same SSID (`option isolate`) is not mentioned.
  The proposal does not require it, so leaving it out is fine. Saying so
  avoids a later reader assuming it.
- `/etc/mjolnir/secrets/` is not in OpenWrt's default sysupgrade keep set.
  If the file is lost, hostapd `touch`es an empty PSK file and the BSS comes
  up with no one able to join. That belongs to `lpv` or the deploy path,
  but it should be tracked.
- Mixed `psk2`/open under one SSID during cutover is `lpv`'s, as above.
