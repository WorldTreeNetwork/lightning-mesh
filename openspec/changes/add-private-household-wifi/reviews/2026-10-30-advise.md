## Blind take (written before opening design.md or tasks.md)

1. Pin: the committed `mjolnir` text lists `10.42.0.0/16` as `closed`. Published `.mesh` hosts, hello.mesh (`10.42.x.1:80`), and the client's own DHCP/DNS gateway all live in that `/16`. If the text is taken literally, it closes what the spec says stays open.
2. Pin: `render_policy` takes only the SSID. The published-name set, the reach decisions, and the classes never reach the committed artifact. So publishing a name does not move the revision, and the reach rules exist only in a test simulation.
3. Pin: the spec says "classify each client flow as a published service". `classify` can only return Member or Unidentified. Either a published service is a destination, not a client class, or the builder owes a path that assigns it.
4. Pin: what a member's verifier answer binds to. On an open SSID, MAC and IP are visible and spoofable, so anyone can take the member mark. The spec should say spoofing gains priority only, never reach. Otherwise "member" will later get used as an access boundary.
5. Pin: what "ahead" means. Strict priority with no floor starves unidentified flows on a saturated link. That is a zero cap in effect, which clashes with "no rate cap" and "best effort".
6. Refuse: a second SSID, a rate cap, membership from association or a label, and a builder that touches `OpenWrtAdapter` or `wireless`. The code does all of this.
7. Refuse: a committed plan with `required_health: []` that a real adapter could submit. Today nothing real implements `SchedulesClients`, so this is safe. Say so.
8. Refuse: treating `extra_ssids` as an invariant. It is a caller-declared input. The builder never reads the deployed `wireless`.
9. Note: the exit test holds. Membership is a user-held IdentiKey and biscuit, and unidentified keeps internet.
10. Tradeoff: strict priority gives members the most on a busy link but can starve visitors. Weighted precedence (Cake tins, WMM AC) never starves anyone but gives members less. The author must pick one, or pin that it must not starve.

## Steelman

The supersession is the right call, and it is clean. One SSID removes the
whole guest-SSID failure surface that r1–r7 kept finding: secret files,
the fleet INPUT gate, guest CIDRs, roam exclusion, and the IPv6 refusal.
What replaces it is honest about what it is: a recorded intention plus a
pure builder that no live adapter can submit. The submit gate is a trait
that `OpenWrtAdapter` does not implement, and a compile_fail doctest proves
it. That is the strongest form of "no live writes" available short of not
writing the function. Classification ignores association and the
directory label on purpose (`let _ =`), and a test covers it. The design
says plainly that priority is not a reservation, which most QoS proposals
leave out. I would make the same top-level choices.

The best defence of R8-1 is that `mjolnir_policy` is "the text a later
adapter would write", and that the later slice will add the published-name
exceptions. But this change commits that text as a revision digest today,
and the spec's second requirement is a reach rule. A committed artifact
that says `closed '10.42.0.0/16'` and does not list the published names
contradicts the contract it is filed under. A later slice would have to
change the format and the revision meaning anyway. That costs less to fix now.

The best defence of R8-3 is that "Cake versus WMM" is rightly deferred.
I agree. What is owed is one sentence, not a scheduler.

## Owed

### R8-1. The committed policy must agree with the reach rule

`render_policy` (`client_class.rs:249`) writes `list closed '10.42.0.0/16'`
next to the overlay and the recovery address, under the doc comment
"Closed to client traffic" (`:22-25`). The spec closes the management plane
(overlay, WAN SSH, recovery) and separately says clients get no route to
every house address. Those are different statements. The `10.42/16`
aggregate also holds every published `.mesh` host (`mesh-mini-apps`
treats it as the app-host range), hello.mesh on `10.42.x.1:80`, and the
client's own gateway for DHCP and DNS.

Owed, pick one:
- (a) Render the published names, or the services they resolve to, plus
  the client's own gateway services (DHCP, DNS, hello) as explicit allows
  ahead of the `10.42/16` deny. Make `render_policy` take the published set
  so publishing a name moves `proposed_revision`.
- (b) Drop `10.42.0.0/16` from `closed`. Record it as a separate
  `no_blanket_route` statement, and say in design.md that the published
  exceptions are the later apply slice's job.

Either way, add a test asserting that a committed policy does not close
a published name's reach.

### R8-2. Published service is a destination, not a client classification

Spec §"Three classes share that SSID" says "The plan SHALL classify each
client flow as a published service, a member, or unidentified." The design
defines a published service as a box that publishes a name, which is a
destination. `classify` never returns `ClientClass::PublishedService`.
Owed: reword the spec so client flows are classified as member or
unidentified, and published services are named destinations. Or, if the
box is itself a client of the SSID, add the input that classifies it and
a scenario for it.

### R8-3. Say whether "ahead" may starve unidentified flows

The spec says unidentified clients keep internet "at best effort", with
"no rate cap". Under strict precedence, a saturated member load gives
unidentified flows zero, which is a cap in effect. Owed: one sentence in
spec and design. Either "ahead" SHALL NOT starve unidentified flows
(weighted precedence, mechanism deferred), or starvation under member
saturation is accepted and stated. Pick one. The mechanism stays not owed.

## Notes (not owed)

- Member binding: on an open SSID, any MAC- or IP-keyed mark can be
  spoofed. Ask `ai0.1` to state that the member mark grants schedule
  order only, never reach. The spec already gives members and unidentified
  clients the same reach, which is the right shape.
- `required_health: Vec::new()` in the committed plan is safe only
  because no real adapter implements `SchedulesClients`. Whoever adds
  the first real impl owes the probes (`2mgv`).
- `extra_ssids` is a declared input. The builder does not observe the
  deployed `wireless`. That is fine for a pure plan, but don't cite it as
  proof that the house has one SSID.
