## Blind take (written before opening design.md or tasks.md)

Sources: proposal.md, `specs/private-household-wifi/spec.md`, the living
`wifi-internet-uplink`, `node-connection-profiles`, and `identity-derived-ula`
specs, the household-network-management requirements, and the cited code
(`model.rs:34`, `uplink.rs:112`/`:227`/`:261`, `roam.rs:33`).

1. Pin: `Plan` is one `node_id`, so cutting the fleet over to `psk2` is N transactions. A mixed state (some nodes open, some `psk2`) will exist. Name who orders the cutover and whether the SSID name stays the same, because a saved open network fails when its security changes under the same name.
2. Pin: a secret-bearing plan must be typed so that `OpenWrtAdapter` cannot submit it, like `ProvesUpstream`. A passphrase-only change leaves `wireless` byte-identical, so netifd will not reload hostapd by itself. The gate must name that reload.
3. Pin: `wpa_psk_file` without `key` works only for PSK, not SAE. Pin the file line shape and the passphrase charset.
4. Pin: the secret file path is derived from the SSID, which is up to 32 arbitrary octets. A root-owned file path built from owner input must be path-safe.
5. Pin: the "drop the guest class" refusal says "every builder that rewrites `mjolnir`". Name where that check lives. Writers outside the crate (hand `uci`, `meshctl`, deploy scripts) are not builders.
6. Pin: the joiner rule ("a joining node carries the class before it exports routes") is a SHALL in this spec, but this change does not edit admission. Something has to carry it, or the scenario cannot pass at fold.
7. Refuse: the default guest plan rejects INPUT except DHCP and DNS. That blocks hello.mesh for guests, which pulls against "visitors can discover the hub" in household-network-management. Either is fine, but the design has to pick one.
8. Refuse: the word "isolated" with no statement about guest-to-guest traffic on the same node (`option isolate`).
9. Tradeoff: refusing guest whenever UCI IPv6 is on is honest, but stock `ula_prefix`/`wan6` make guest unavailable on every node today. Say so.
10. Pin: Babel's return route for a satellite guest CIDR and the `guest_routes` `/32` exclusion are meshd work. Each needs an owner (a task or a bead).

## Steelman

The design is careful and tight. Almost everything in my take is already
there, in plain words. It follows the uplink secret precedent exactly,
down to reusing `Passphrase`, whose charset already rules out a second
file line. The isolation gate uses aggregates, not peer lists. The class
lives in committed config, not in a fleet object nobody applies. It
refuses IPv6 instead of half-building a v6 deny, sets `ipv6 '0'` on the
guest device, and says out loud that guest is therefore unavailable on
today's fleet. It is upfront about the residual peer-revision window.
The hello.mesh and `option isolate` choices are both made explicitly.
The return route already has a bead (`mzgw`). I would make the same
choices.

The two items below are not design disagreements. In each, a sentence in
the spec promises something nothing in this change or the bead graph
delivers or pins.

The strongest defense against R6-1 is that the joiner rule is a guard
rail for a path that is not built yet, and the builder already treats an
uncovered joiner as not covered. That handles *new* guest plans. It does
not handle the scenario the spec writes down: a guest SSID is already
committed and a joiner exports routes without the class. Then guests on
N can reach the joiner's non-aggregate addresses (its WAN or `wwan`) and
any service the joiner exposes on them. The only thing that stops this
is the admission rule, and nothing tracks that rule. Since guest is
refused fleet-wide today, the risk is latent. That is why this asks for
an owner, not a redesign.

The defense against R6-2 is that an implementer copying `uplink.rs`
would hash the name anyway (`candidate_id` is a domain-separated
blake3). That is likely, but the uplink path is keyed on a hash it
already pins. This one is keyed on owner-typed SSID bytes, and the file
is written as root. One sentence closes it.

## Send-back items

### R6-1: The joiner rule has no carrier (blocking, small)

Spec: "While a guest SSID is committed, a joining node's admitted config
SHALL carry that class before the node exports routes." The scenario
"A joiner has not carried the class" asserts that the node "does not
export routes until admission includes the class". This change edits no
admission path. `add-zero-touch-join` has no guest-class requirement or
task, and no bead names it (`bd search guest` returns `mzgw`, `ai0.7`,
and `ai0.1` only). Today's non-fyby join (a peer file plus the deploy
install) is also a join, and nothing gates its route export either.

Owed, either:
- file a bead (under `mjolnir-mesh-fyby`, covering every join path,
  not only zero-touch) whose acceptance is "a node does not export
  routes while a committed guest-source class it lacks exists", and cite
  it in design.md and next to the spec SHALL; or
- reword the SHALL and the scenario so this capability states only what
  this change verifies (an uncovered joiner is not counted and blocks new
  guest plans), and move the export hold into that bead.

### R6-2: The secret file name must be path-safe (blocking, wording plus a test)

`/etc/mjolnir/secrets/wifi/<profile-id>` is written as root, and
`<profile-id>` is "derived from the SSID and the role". SSIDs are up to
32 arbitrary octets, so `/`, `..`, NUL, and non-UTF-8 bytes are all
possible.

Owed: pin the derivation as a fixed-alphabet encoding, for example
lowercase hex of a domain-separated blake3 over role plus SSID bytes, as
`candidate_id` does in `uplink.rs`. Add a builder test with an SSID
containing `/` and `..` that still yields a file directly under
`/etc/mjolnir/secrets/wifi/`. While editing, say "the file is exactly one
line" rather than "each line".

## Notes (not blocking)

- The in-crate writers of `mjolnir` (`node_profile.rs` `render_mjolnir`,
  and `uplink.rs`) edit named sections in place, so they keep a guest
  class section. A regression test on each, inside the existing "drop
  refused" task, would make the "every builder" sentence true by test,
  not by inspection. Hand `uci`, `meshctl`, and deploy scripts are not
  builders and are not covered. Say so in a clause.
- "Every house node rejects INPUT" is met by the class in committed
  `mjolnir` config. Rendering nftables is not owed here. Name the bead
  that renders it (or file one) so "isolated" in a plan is not mistaken
  for "enforced on the router".
- A mixed `psk2`/open cutover under one SSID name belongs to `lpv`.
  Check that `lpv` names it.
- Changing an SSID makes a new profile id and a new secret file. Old
  files are kept for restore, but nothing ever removes them. That is
  harmless for now; worth one line in Not owed.
