## Blind take (written before opening design.md or tasks.md)

1. Pin the secret mechanism. The AP takes its key from `option wpa_psk_file` or
   `sae_password_file`, which names a root-only file. Refuse `option key` and
   `config wifi-station … key` in `wireless`. The two files have different
   shapes (psk: `00:00:00:00:00:00 <pass>`; SAE: `<pass>|mac=ff:…`), so pin
   the encryption mode (psk2, sae, or psk-sae) together with the file shape.
2. Keep parity with the uplink secret rules that the delta spec dropped:
   - The transaction snapshots and restores the secret file.
   - A monotonic `secret_generation` in `mjolnir` makes a passphrase-only
     rotation move the revision.
   - No manifest, revision, or receipt holds an unkeyed hash of the file.
3. Pin where isolation is enforced. Guest traffic MUST cross nodes to reach the
   gateway's WAN. So "deny cross-node" has to be a destination deny at the
   guest's ingress node, over the resident aggregates (`10.42.0.0/16`,
   `10.254.0.0/16`, RFC1918, and ULA plus house GUA for v6). It cannot be
   "deny forward to mesh". It also cannot be a list of today's peers, which
   goes stale when a node joins.
4. Pin the guest zone's input chain. Resident services on the same node include
   the router itself: SSH on the overlay address, mjolnir-hello on
   `10.42.x.1:80`, and LuCI. Input is REJECT, and only DHCP, DNS, ICMPv6-ND and
   RA are accepted.
5. Read "IPv6 enabled" from the committed config, not from a caller flag. When
   it is unknown, fail closed: refuse the plan, or plan with guest v6 off.
6. Pin the guest prefix against `roam.rs`, which treats any foreign `10.42/16`
   address on the client bridge as a roamer. A guest `/32` must never land on
   `br-lan` or be exported as resident. Say whether guests can roam.
7. Don't let spec scenarios claim radio behaviour ("association requires the
   passphrase") when this change ships only a pure builder with no live
   adapter. Restate them over the planned config.
8. Decide whether guests see hello.mesh. The household spec wants visitors to
   find the hub, but the hub binds resident LAN addresses. The plan needs
   either a named exception or a statement that guests do not see hello.mesh
   in this change.
9. The uplink's house-SSID refusal must follow a renamed resident SSID and the
   guest SSID.
10. Tradeoff: same SSID name or a new one. Keeping the name means owners
    relabel nothing, but a leaf-first rollout with per-node rollback leaves a
    mixed-security ESS. A new name gives a clean cutover, but every phone has
    to rejoin. The author must pick one and say so.

## Steelman, then the owed items

**N1 (take 1, 2). The secret has to reach hostapd without being in `wireless`.**
Steelman: the uplink precedent already asserts `!wireless.contains("option key")`,
so the author can say it is inherited. It isn't fully inherited, for two
reasons:
- The uplink file holds the raw passphrase. hostapd's `wpa_psk_file` needs
  MAC-prefixed lines, and `sae_password_file` has its own syntax. If the
  builder points `wpa_psk_file` at a raw-passphrase file, hostapd can't parse
  it and the AP is down. With `band == 6g`, `ap.uc` skips the psk file
  altogether.
- The folded spec is the contract. Without the snapshot/restore and
  no-unkeyed-hash rules, it is weaker than the living uplink spec it cites.

Owed:
- In the spec, the resident and guest `wifi-iface` carry no `key` and no
  `wifi-station` key. They name the root-only file through `wpa_psk_file` /
  `sae_password_file`.
- Design names the encryption mode and the file's line format.
- Spec adds three rules:
  - The transaction snapshots and restores the secret file.
  - A passphrase-only change moves the revision through a `mjolnir`
    generation.
  - No revision, manifest, or receipt carries an unkeyed hash of the file.
- `<profile-id>` is derived from SSID and role, never from the secret.

**N2 (take 3, 4). Isolation needs an address basis and a protected egress.**
Steelman: design marks nftables rendering as not owed. "The plan states the
denies" is abstract on purpose. But the gate checks the denies as stated, so
how they are stated is part of the plan object, not a rendering detail. Two
failures fit the current text and pass every listed test:
- Per-peer deny. The guest node's plan enumerates current resident `/24`s. It
  reads `isolated` at build time. It stops being true when a new node joins,
  and the guest node's revision never changes.
- Over-deny. "Guest → mesh: deny" meets both deny bullets, but guests on every
  satellite lose internet, because their only path to the WAN is the mesh.

Owed:
- Spec says the cross-node deny is a destination deny at each guest-serving
  node, over house aggregates. For v4 that is the client space, the overlay
  `/16`, and the recovery and private ranges. For v6 it is ULA plus the house
  prefixes.
- "Resident addresses on the same node" includes the node's own addresses.
  Guest input permits only DHCP, DNS, and ND/RA (v6).
- One scenario: a guest on a satellite reaches the internet through the
  gateway while a resident address on that gateway is denied.

**N3 (take 5). "IPv6 enabled" needs a source and must stay true.**
Steelman: the design already refuses an IPv6-less isolation claim when v6 is
enabled. But "enabled" is an input, and nothing stops a later plan from turning
v6 on, for example an uplink that brings up `wan6` or an `ip6assign` change.
After that, a v4-only `isolated` guest profile is a false label.

Owed:
- The builder derives IPv6 state from the committed `network` / `mjolnir`
  config. If it can't tell, it refuses.
- Spec states the cross-plan rule. A plan that enables IPv6 while a committed
  guest profile has no v6 deny is refused, or it carries the v6 deny in the
  same revision.

**N4 (take 6). Guest addressing against roam.**
Steelman: which radio serves clients is `mjolnir-mesh-lpv`. But the guest
bridge and its prefix are `network` config that this builder emits, and
`roam_loop` acts on the client bridge.

Owed: design names where the guest prefix comes from, and states two things:
- `roam` never installs a guest `/32` on `br-lan`.
- Whether guest roam across nodes is supported in this change. "No, guests
  re-DHCP" is an acceptable answer.

**N5 (take 7). Spec overclaims radio effect.**
The "Owner commits the resident plan" scenario says "association to the
resident SSID requires that plan's passphrase". This change has no live
adapter, and live radio writes belong to lpv, so the scenario can't be
observed here.

Owed: restate it over the committed plan. The desired `wireless` has no open
client `wifi-iface`, and the resident iface uses the pinned encryption and
names the secret file. Leave the association claim to lpv's probe.

**N6 (take 8). Guests and hello.mesh.**
Steelman: CAPPORT and the welcome page are out of scope. But whether the
default guest plan denies `10.42.x.1:80` is a plan default, not a welcome-page
behaviour. It collides with household-network-management's "anonymous hub
browsing" scenario.

Owed: one sentence in design naming the default. Either hello.mesh is a named
exception in the default guest plan, or guests don't reach hello.mesh until a
later change.

## Notes (not owed)

- The "Builder is invoked in tests" scenario can't really prove that a call
  didn't happen. The uplink shut that door at the type level with
  `ProvesUpstream`, which `OpenWrtAdapter` doesn't implement. Do the same here
  so the test asserts something real.
- For `mjolnir-mesh-lpv`: decide whether to keep the `Lightning Mesh` name
  under new security (mixed-security ESS during a leaf-first rollout with
  per-node rollback) or to cut over to a new name. Also check that
  `setup-wireless.sh` FT-PSK (`ft_psk_generate_local`) still works when the PSK
  comes from `wpa_psk_file`.
- Proposal says "cross-node guest reachability", and the spec says "guest
  reachability to resident addresses". Make it clear whether guest-to-guest
  across nodes is also denied. The aggregate deny in N2 denies it if guest
  prefixes sit inside the client space.

## Verdict

Send-back. The direction is sound and the pins in design.md are the right
ones. N2 is the architecture gap: as written, the isolation gate can be met by
a plan that goes stale on the next node join, or by one that cuts guest
internet on every satellite. N1 is a correctness gap: a raw-passphrase file
named as `wpa_psk_file` takes the AP down. N3 to N6 are one to three sentences
each. Owed boxes are added to tasks.md, and the fresh-advise box stays open.
