## Blind independent take

Written before opening design.md, steer.md, or tasks.md. Inputs were the proposal, the
delta spec, the living spec, and `admin/src-tauri/src/canvas.rs` (plus `stdout.rs`, which
`CanvasState` embeds).

1. Pin: the well identity for fill and cancel comes from the calling window's label, which
   Tauri injects. A frontend-supplied id is not acceptable. Today `fill_canvas_source(name)`
   takes no id, and `CanvasState.source` is one shared `Running` with one generation counter.
   Two wells would each supersede the other's fill.
2. Pin open semantics. Today `open_with` reuses and focuses `CANVAS_ID = "canvas-well"`. The
   contract must say that opening another well creates a new `canvas-*` label, and it must
   say how the operator asks for one.
3. Pin a maximum well count. Each well costs a vibrancy webview and up to one child process.
   The spec names no bound.
4. Pin destroy isolation. `CanvasState::remove` calls `source.deactivate()` for the whole app.
   Closing one well must reap only that well's child.
5. Pin failure isolation as a scenario. The proposal's "Failed" journey says a timeout in one
   well leaves the other's transcript alone. The spec does not test this.
6. Pin "placed in a grid": who places a new well (for example, the next free cell from the
   last position) and whether Control-drag still moves it freely afterward.
7. Refuse: a saved layout, a shared or app-global child, and any new source. The delta spec
   already does this.
8. Smell: the MODIFIED requirement keeps the title "One canvas in this landing" while its body
   allows more than one. It should be renamed.
9. Tradeoff: N OS windows reuse the chrome and gesture contract as they are, with no layout
   engine. The costs are N webviews and N masks, and the grid has no shared frame because each
   window moves alone. One container window would give a shared frame, but it needs a new
   layout surface. Several overlays is the cheaper choice.
10. "A third source name is refused" is already living behavior, so restating it is harmless.

## Comparison and steelman

`design.md` and `steer.md` agree with the steered direction: several owner-drawn windows,
session-only placement, no 3d engine. I have no objection to the direction. Steer's "[AUTO]
Each well keeps its own allowlisted source and its own child" and the delta's "Each well SHALL
keep its own ... in-flight child" show the author saw take 1 at the level of intent.

The steelman for accepting is that the living "Allowlisted stdout well" requirement already
says "at most one child process SHALL run *for a canvas*" and "destroying the canvas SHALL cancel
and reap *its* child". Read literally, the contract is per-canvas already. Re-keying
`SourceState` by label would be implementation that satisfies an existing requirement, not a
new decision. I accept that argument for the wording.

It does not cover the architecture. The design's only pin about code is that "two visible wells
need two ids." The real structural change is moving the child, the generation counter, and the
`open` flag from app-global to per-label. It also has to decide where the IPC learns the label.
That is the one place a naive implementation goes wrong in a way the scenarios would not catch.
Both delta scenarios ("Two wells at once" and "Focus keeps the other well") pass even if a fill
in well A cancels well B's in-flight child, provided B is re-filled later or was already
complete. The proposal's Failed journey is the scenario that would catch this, and it is
missing from the spec.

Items 2, 3, and 6 are also open in design. "Placed in a grid" has no placement rule, and nothing
says how the operator opens a second well while today's `open_canvas` focuses the existing one.
Item 8 is a mechanical fix.

## Owed before acceptance

### R1 — Blocking: per-well child isolation is untested
Add a scenario to "Grid of stdout wells": GIVEN well A with a running fill, WHEN well B starts
a fill or swaps source, THEN A's child is not terminated and A's result still paints. Add a
second scenario: closing one well reaps only its own child, and the other well's in-flight
fill completes. Pin in the requirement or design that the well id for fill and cancel comes
from the invoking window's label and is never an IPC argument.

### R2 — Blocking: open semantics and bound
State how a second well is opened and that it mints a new `canvas-*` label rather than focusing
the existing one. State the maximum number of wells, or explicitly justify having none, and say
what happens when that maximum is reached.

### R3 — Placement rule
Give the rule "placed in a grid" uses for a new well's initial position, for example the next
cell offset from the existing wells and clamped on-screen. Confirm that the existing Control-drag
and Option-resize gestures apply per well and are not snapped back.

### R4 — Failure and Off isolation
Add the proposal's Failed journey as a scenario: a timeout or refusal in one well leaves the
other well's transcript intact. The non-macOS "unsupported, no spawn" behavior per well can
remain implied by the living requirement.

### R5 — Housekeeping
Rename the MODIFIED "One canvas in this landing" requirement, for example to "Canvas count",
using the RENAMED form so the title matches the body after the fold.

## Not owed

- The direction itself: several overlays, session-only placement, the 3d spike skipped.
- Any new source or data-plane change. None is proposed.
