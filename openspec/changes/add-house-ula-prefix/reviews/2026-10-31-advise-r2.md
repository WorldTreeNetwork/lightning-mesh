## Comparison with the previous review

**R1 is resolved.** `design.md:11–19` pins the 20-byte domain without a terminator, raw guild bytes, router UTF-8 string input, raw app public-key input, network byte order, subnet ids, and zero-IID clamp. The delta carries that contract and literal router/app/legacy examples. I independently recomputed all six design-table vectors with Python's BLAKE3 implementation and compared parsed IPv6 values; all six match. The router string convention preserves the existing `ula_addr` behavior. This answers blind concerns 1–6 without requiring a new identity representation.

**R3 is resolved.** The modified identity requirement now states the 40-bit prefix and 64-bit IID collision limits, including the inherited legacy limitation. The two-house scenario is explicitly about fixed fixtures. It no longer promises universal uniqueness or requires collision allocation. This answers blind concern 7.

**R2 is partly resolved and remains blocking.** The amendment pins ASCII trimming, case-insensitive hex, startup/reconcile reads, exact `/128` assignment, current-interface publication evidence, invalid-file handling, and interface recreation. It retains the legacy `/64`, Babel deny, and Iroh exclusion. Those are substantive improvements, and the delta preserves the operational requirements relevant to blind concerns 8–10. The remaining issues are narrower than the original R2:

1. **Restart ownership is still asserted rather than defined.** `design.md:42–46` promises removal of an older guild's address while the delta at line 43 permits deletion only of the address the daemon previously assigned. Consider: assign guild A, terminate the daemon while its kernel address survives, replace or remove the guild file, then start a new process. The current file supplies no old guild A, and neither document identifies restart-surviving ownership evidence or an explicit reset procedure. The new process cannot select the old address safely merely from its differing prefix. Specify how the old owned address is identified across restart, or choose the explicit bounded reset procedure allowed by the first review. Preserve the prohibition on deleting unrelated addresses. Include the restart case in the delta; the present change scenario does not establish it.
2. **The assignment-state boundary still needs an explicit decision.** `design.md:46` defines assignment as address/prefix presence and says a failed add does not count, but does not discuss tentative or DAD-failed entries, as the first review requested. State whether those entries may publish `house_ula`, and distinguish an unsuccessful add with no matching address from an add that reports an error while the exact desired `/128` already exists. Existing-address observation can be authoritative; there is no requirement to build a new state service. The chosen semantics must agree in design, delta, and acceptance cases.
3. **The requested lifecycle acceptance cases are incomplete.** The delta adds missing/malformed-file and guild-change cases, but has no explicit cases for failed add, already-present correct `/128`, interface loss/recovery, or restart with a changed/removed guild file. `tasks.md` only schedules fixture-vector tests. Add focused parser/state/publication checks and an assignment integration check covering these transitions, including the address-state decision above. These are acceptance obligations for implementation, not a request to run product tests during this review.

The cited daemon code explains why these details cannot be inherited implicitly: `assign_ula_addr` returns no assignment result (`mjolnir-meshd.rs:7653`), legacy publication is derived unconditionally (`:3386`), and the current reconciliation loop restores only its supplied legacy address (`:7527`). The amendable contract, rather than the reader, must choose the new ownership and publication rules.

## Steelman against the blind take

The Why emphasizes a pure prerequisite, but the proposal deliberately includes optional daemon assignment and publication. That is a reasonable small scope extension: dual assignment protects existing management access while consumers migrate. The author has already chosen periodic reconciliation, so a watcher, forwarding spike, membership verifier, collision coordinator, or Admin integration would add no value to this gate. I accept the explicit string-based router input and probabilistic collision tradeoff.

The strongest reading of the amendment is that “previously assigned” includes a former process and “currently has” means a usable address. Under that reading, the intended behavior is sound. However, those interpretations do not specify how restart ownership is established or whether tentative/failed entries qualify, and the missing acceptance cases would not expose an implementation choosing differently. A short lifecycle amendment is sufficient; a competing architecture is unnecessary. `Unverified hypotheses` says none. A focused assignment-state spike remains an option before implementation if needed; cross-site reachability remains out of scope.
