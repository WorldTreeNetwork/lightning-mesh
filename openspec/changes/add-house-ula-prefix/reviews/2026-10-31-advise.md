## Independent take — recorded before reading design or tasks

1. Pin the exact guild-id bytes, hash domain, byte order, and truncation that define the house `/48`; this becomes a durable addressing contract.
2. Pin router and app subnet assignments and canonical identity inputs so different callers derive identical `/128`s.
3. Preserve the current `ula_prefix()` and `ula_addr()` outputs and legacy `/64` attachment with regression vectors.
4. Require deterministic fixtures for same-house agreement, different-house separation, node separation, and router/app separation.
5. Refuse an address derived from a display name, gossip topic, IPv4 address, or an unvalidated textual guild identifier.
6. Pin missing, malformed, changed, and removed guild-file behavior, including whether changes take effect at startup or during reconciliation.
7. Publish `house_ula` only under a defined assignment-success condition, and specify failure and stale-address cleanup behavior.
8. Refuse implicit routing, Iroh candidate admission, or membership authority merely because a house address exists.
9. State the probabilistic collision limits of the 40-bit prefix and 64-bit IID rather than promising universal uniqueness.
10. Tradeoff: dual assignment preserves current on-link management, but the new `/128` alone must not be presented as providing cross-node reachability.

## Comparison with the authored contract

The direction is sound. `design.md` pins raw guild bytes, a separate versioned hash domain, the 40-bit prefix, subnet ids 0 and 1, and the zero-IID clamp. It explicitly preserves the legacy `/64`, avoids a covering house prefix, and keeps both Iroh binding and forwarding outside this change. `tasks.md` supplies the missing/malformed-file fallback. The spec delta preserves the on-link SSH, Babel-deny, and stock-ULA filtering requirements. These answer blind concerns 1, 3, 5, 8, and 10 in substance.

The remaining problems are contract gaps at the boundary between pure derivation and daemon state. They are fixable without changing the architecture or taking on a later campaign node.

## Required revisions

### R1 — Pin the complete address derivation, not just the guild input

`design.md` / Derivation and the spec delta say `blake3(node_id)` and `blake3(app_public_key)` without defining their byte encodings. The existing `ula_addr(node_id: &str)` hashes UTF-8 string bytes (`crates/mjolnir-mesh/src/tun/link.rs:63`); its daemon caller supplies `secret.public().to_string()` (`crates/mjolnir-mesh/src/bin/mjolnir-meshd.rs:430`). A future Admin caller hashing raw key bytes can therefore disagree with a router caller hashing the displayed key, while both satisfy the written formula. The app function is a contract for that later caller even though this node does not wire it into Admin.

Define the canonical router-id input and app-key input, domain bytes without an implicit terminator, and network-byte-order placement of subnet and IID bytes. Keeping the current router string encoding is acceptable; using raw bytes for the new helper is also acceptable if explicit and consistently consumed. Do not change legacy derivation. Add literal expected-address vectors for representative guild/router/app inputs and a legacy regression vector; repeated calls and a domain-inequality assertion alone will not catch an accidental encoding or domain change.

### R2 — Define assignment lifetime and make publication evidence explicit

`design.md` / Assignment promises `house_ula` only when assigned, but the tasks only say omitted when unset. Existing machinery does not supply that guarantee automatically: `assign_ula_addr` returns no success state (`mjolnir-meshd.rs:7653`), `stamp_node_link_locals` unconditionally derives the legacy `ula` (`:3386`), and `reconcile_backhaul_addr` restores only the supplied legacy ULA after an interface reload (`:7527`). Copying the current publication pattern would publish a desired house address after a failed add, or continue publishing it after `br-mesh` loses the address.

Pin when the guild file is read, how surrounding whitespace and hex case are handled, and what changed/removed/malformed configuration means after a successful assignment. Startup-only loading is a valid bounded choice; a live file watcher is not required. Specify restart behavior when an old house address survives in the kernel, including ownership-safe cleanup or an explicit reset procedure. Do not leave stale-address retention implicit or flush unrelated IPv6 addresses.

Define what counts as assigned (including the intended treatment of tentative/failed addresses), how the house `/128` is restored after interface recreation, and how directory output observes that state. Add acceptance cases for absent/malformed configuration, add failure, already-present correct `/128`, interface loss/recovery, and a guild change/removal at the chosen reload boundary. These cases can use focused parser/state tests and an assignment integration check; no cross-house forwarding or fleet deployment is needed for this review.

### R3 — Replace the impossible uniqueness requirement

The modified identity requirement says “Distinct guild ids SHALL produce distinct `/48`s.” A 256-bit input space mapped into 40 bits cannot meet that requirement. The same block repeats the inherited absolute node-address uniqueness claim despite the 64-bit truncated hash and zero-to-one clamp. A two-input test demonstrates one fixture pair, not universal uniqueness.

State deterministic, probabilistic separation and its collision limitation. Scope the two-house scenario to fixed example ids known to produce different prefixes, and qualify the inherited node uniqueness wording while replacing this requirement block. Collision detection or allocation machinery is not required in this node; an honest contract is.

## Steelman against the independent take

This is intentionally a small prerequisite: the author should not need a forwarding spike, guild-membership verifier, collision coordinator, or Admin integration to land a deterministic helper and an optional address. The existing string-based router helper is a reasonable convention to reuse. “Only when assigned” already expresses the correct publication intent, and normal implementation judgment can choose netlink observation or tracked state. The legacy address protects current operator access, so failure of the new address need not become a daemon-startup failure.

Those arguments narrow the revisions above. They do not justify leaving the app's hashing bytes unspecified, promising mathematically impossible uniqueness, or allowing two implementations to disagree about which house address survives a restart and is published. A short contract amendment plus focused acceptance cases is sufficient; this is not a request for a competing design.

The `Unverified hypotheses` section says none and explicitly delegates reachability to `add-ula-host-forwarding`. A spike remains an option before implementation if assignment-state handling proves uncertain, but cross-site reachability is not a condition of this review.
