## 1. Blind pass (written before opening design.md / tasks.md)

From `proposal.md` **Why**, `openspec/specs/living-specs/spec.md`,
`crates/mjolnir-hello/src/portal.rs`, and
`docs/standards/identikey-capability-v1.md` only. What I would pin / refuse / one
tradeoff:

1. Pin ONE canonical, domain-separated, length-framed encoding for the signed
   tuple (token-identity ‖ verifier-nonce ‖ audience = node + operation ‖ optional
   response-key), byte-exact, shared signer↔verifier. This is the whole ballgame.
2. Pin the trust boundary: the verifier is the SOLE injector of `holder(fp)`,
   `time`, authority-epoch-floor and any count facts; reject any token that
   asserts those (especially `holder`) — cf. IdentiKey §7.1.
3. Holder proof = signature by the named key over the canonical tuple; fingerprint
   = Blake3 of the self-describing pubkey (auth-challenge §5); fail closed.
4. Approved-issuer set + epoch floor are construction-time anchors, never
   token-derived; untrusted root → typed denial; epoch < floor → stale-authority
   denial.
5. Refuse membership / role / association / public identity as authorization; only
   an owner grant naming operation + node + holder authorizes; never fall back to
   SSH or a role label. (portal.rs invariant: public identity is not administration.)
6. Grant ceiling is monotonic: attenuation only narrows; a narrower owner op passes,
   any widening / other-node / other-op fails.
7. Freshness = nonce + expiry + epoch, but this library CANNOT *prevent* replay (no
   durable state) — it must honestly state that nonce reservation/burn is the
   consumer's (b6j.2) obligation.
8. Refuse to claim conformance to identikey-capability-v1 for the tuple encoding —
   upstream defers it (`ikp-6yz.2`; "not independently implementable, no vectors");
   own a local *versioned* pin instead.
9. Tests must structurally separate verifier-facts from token-facts and cover all
   five negatives (membership, altered-holder, untrusted-issuer, stale-authority,
   replay).
10. Tradeoff: a local encoding pin now unblocks the enforcement boundary but creates
    reconciliation debt — acceptable only if that debt is recorded and versioned,
    not silently passed off as the upstream contract.

competing design):

**Acceptance (`contrast`) is satisfied.** The contract cleanly distinguishes a valid
narrower owner-authorized operation from each attack class, with honest
implementation boundaries:

- **valid narrower op** — *Attenuation contrast*: diagnostics on one node succeeds,
  configuration / the other node is refused.
- **membership / role** — excluded at context construction; authorization requires an
  owner-approved, holder-bound grant, not a role or directory fact.
- **altered holder** — "changed holder" red vector; "Holder changes SHALL require new
  authorized issuance rather than weakening an existing holder check."
- **untrusted issuer** — external issuer pins + "wrong issuer" red vector.
- **stale authority** — epoch in context; "uncertain time" vector; renewal requires
  fresh verified authority/revocation state; traffic does not extend expiry.
- **replay** — decision is bounded; durable reservation is b6j.2's; no permissive
  in-memory fallback is allowed to stand in for it.

The verifier-fact / token-fact separation (the Why's central demand) is enforced
both structurally (design: "make it impossible for an unverified public request
struct to masquerade as a verified holder"; "No exported bool such as is_admin or
signature_verified is an authorization credential") and by test (forged-fact
vectors in **both** root and appended blocks).

## 3. Genuinely missing upstream contracts — pin-before-code, not send-back

These are real gaps to *implementation*-readiness. None is a spec contradiction;
each is an upstream contract the design already externalizes and gates before
coding. They are recorded here as blockers for the implementation packet
(mjolnir-mesh-ai0.1), for the conductor to track in beads — no task checkboxes.

- **B1 — "token identity" is undefined.** The canonical request binds "token
  identity," but IdentiKey §7.1 explicitly defers *the definition of token identity*
  to Mjolnir `add-biscuit-runtime` / `ikp-6yz.2`, and neither design nor delta pins
  it (Biscuit revocation id? Blake3 of the authority block? full token bytes?).
  Without this the signer and verifier cannot agree on what the signature covers.
  The implementation packet MUST pin one definition and record it as a local pin, not
  claim upstream conformance.
- **B2 — byte codec selection is deferred and the "reuse" path may be empty.** Design
  prefers to "reuse existing compatible IdentiKey encoding rather than define an ad
  hoc serializer," yet the same document states upstream is "a draft with missing
  vectors" and "not independently implementable." There may be **no** frozen upstream
  codec to reuse. Resolve explicitly at pin time: either cite the concrete IdentiKey
  encoding revision reused, or declare the local mesh codec authoritative + versioned
  with a recorded reconciliation dependency on `ikp-6yz.2`. (This is the tradeoff in
  blind point 10; the design's fallback clause covers it but the choice is not yet
  made.)
- **B3 — Datalog third-party-block policy for v1 is unstated.** Design requires
  explicit "Datalog trust scopes and evaluation/resource limits" and forged-fact
  vectors in appended blocks, but does not say whether Biscuit **third-party blocks**
  are accepted. IdentiKey §7.3 puts Identikey-signed (third-party) hops out of v1;
  the mesh profile should mirror that and **reject third-party blocks in v1**, so the
  trust scope of appended-block facts is unambiguous. Recommend stating this
  explicitly plus concrete evaluation limits (max facts / iterations / block count).
- **B4 — holder-proof algorithm set for v1 is unpinned.** auth-challenge §3.1 admits
  ed25519 / p256 / ml-dsa; the mesh profile should name which are accepted for the v1
  holder signature (and PQ-implies-classical handling), so "arbitrary algorithm
  aliases are not compatible substitutes" has a concrete allow-list.

## 4. Hardening notes (optional; not blockers)

- **Reject-minted-holder-fact, not just ignore it.** The delta refuses forged holder
  facts as *evidence* ("cannot satisfy verifier-only predicates"), which is
  sufficient for safety. IdentiKey §7.1 is stricter: a minted token whose
  authority/attenuation block asserts a `holder` fact SHALL be **rejected**. Adopting
  the stricter rule (defense in depth against future predicate-name reuse) and a
  vector for it would tighten the boundary. `time` / `epoch` / count facts deserve
  the same treatment.
- **Challenge issuance vs verification.** The delta says "target-issued one-use
  challenge," but the library has "no live endpoint." Confirm the API *consumes* a
  verifier-supplied challenge (issuance + one-use reservation live in b6j.2), so the
  "target-issued" wording does not imply this library mints or reserves nonces.
- **Trusted-time input contract.** Design correctly refuses a caller-supplied wall
  clock and demands the library "specify exactly what its trusted-time input
  proves." Ensure that specification lands as an explicit input-type in the API
  (verified-time evidence), so a regressed/absent clock denies rather than defaults.

## 5. Verdict rationale

Accept for **specification** review. The contract makes every distinction the
acceptance test requires and is honest about the boundaries it cannot cross without
a live endpoint (replay prevention, revocation distribution, time-evidence
primitive). The four missing items in §3 are upstream contracts the design itself
mandates pinning **before** implementation acceptance and about which it refuses to
fake conformance — that is the correct seam between spec and implementation, not a
defect in the spec. Demanding they be byte-frozen in the delta would conflate spec
review with implementation. Route the §3 items to the implementation packet as
recorded dependencies; do not treat the absence of upstream `ikp-6yz.2` vectors as
this change's failure.
