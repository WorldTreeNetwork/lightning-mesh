1. Pin: gossip is a relay swarm, so iroh proves the relayer, not the author. `LeaseRelease`, `SubnetClaimRelease`, `ServiceUnpublishV2` carry no subject or no signature today; every durable mutation needs subject id plus author signature verified at apply.
2. Pin: the signing input must be a versioned, domain-tagged explicit message (the `mjolnir-name-claim:v1` shape), not "postcard of the struct". A `#[serde(default)]` trailing field (`LeasedName::scheme`) already changes struct bytes across versions and would break verification fleet-wide.

9. Tradeoff: signed-only release with no claim TTL orphans the `/24` of a node that loses its key; R5 revocation has to be the named exit.

### Send-back reason

**S6. The S5 binding, read literally, regresses guest roam (sz9).**
Delta line "A router-id SHALL only originate prefixes it is authorized to
claim" plus the scenario "E originates `10.42.99.0/24` under E's own
router-id ... other nodes do not install" describe exactly what the
roam loop does on purpose. `roam.rs` installs a host `/32` for a phone
that kept another node's IP; `babel/config.rs`
`mobility_redistribute_line` exports it (`redistribute proto 158 allow`)
so inbound follows the client. That `/32` sits inside the *home* node's
claimed `/24` and is originated by the *visited* node under the visited
node's router-id. It is a kernel route, not a CRDT claim, so no grant
covers it. An act that implements 661 faithfully renders origin filters
from claims and every other node drops the roamed `/32`; inbound
blackholes at the home node, which is the sz9 failure verbatim.
CLAUDE.md warns "Do not drop `pub mod roam`. Field validation is `0pv`."
Nothing in design.md, tasks.md, or the delta mentions roam, mobility,
`/32`, or proto 158. The 661 box's "property-red" tests will not catch
this because roaming is not in its scope.

The fix is a decision, not a mechanism. Either:
- **(a)** mobility host routes are a named carve-out: a `/32` inside the
  mesh client space originated by any enrolled router-id with a live
  session SHALL install, and enrolled-insider hijack of a single client
  `/32` is accepted R5 residual (same class as the origin-forgery
  residual already pinned); or
- **(b)** roam becomes a signed CRDT lane (visited node signs a mobility
  record for the client `/32`) and 661 filters read it. Heavier; changes
  sz9's design; probably not this change.

Owed: one sentence in the 661 requirement choosing (a) or (b); a
scenario "roamed client `/32` from an enrolled visited node still
installs"; a line in design.md Pins naming the residual if (a).

### Notes (not blocking)

- **N10 canonical bytes.** Take 2. "Canonical bytes" and "same shape as leased-name claims" should be read as a versioned, domain-tagged explicit message per lane and per mutation type, not the postcard encoding of the entry. Postcard is not self-describing and `#[serde(default)]` fields shift the bytes across versions. A message-type tag also removes any claim-vs-release confusion for the same key and HLC. One design line under the S4 pin would stop act from signing struct bytes.
- **N11 frozen means dropped.** Take 3. The spec's "merge SHALL verify the signature" already forces unsigned legacy variants to be rejected once fyby.3 is enforced. Design "old variants freeze" should say decode-and-drop, not D-004's keep-applying, so the gate cannot be downgraded. The persisted-book load pin covers upgraded nodes during rollout; a node with a fresh book during the window could re-claim an old node's `/24`, which the sequential health-gated rollout keeps short.
- **N12 router-id is unbound at HEAD.** Take 4. Neither the config render nor the init script sets a router-id, and babel-routing.md §9 documents `random-id true`. Origin binding needs router-id derived deterministically from the node id (or self-announced in a signed record) and rendered into babeld.conf, and §9 retired. Act cannot render `in id <router-id>` filters any other way, so this is forced by construction, but the doc should not contradict it.
- **N13 filter churn and kf7.** Take 8. Per-claim `in` filters change babeld.conf whenever the claim set changes, which restarts babeld fleet-wide (m8t). Claims change on enrollment, which is rare; acceptable, but the design should note it, and 661 should prove `in ... id ...` on babeld 1.13 hardware, since `le/ge` on `redistribute` silently exported nothing (kf7).
- **N14 revocation evicts.** Take 9. With signed-only release, a dead identity's `/24` persists until revocation. The grant check at merge is the exit, but persisted claims already in the book must also be dropped when the grant is revoked, not only future merges. One sentence under R5 residual.
- **N15 stale claim in design.** "`leased_name` already does this" is still in design.md; r2 established that meshd does not re-verify at merge at HEAD. Wire shape yes, merge check no. Wording only.
