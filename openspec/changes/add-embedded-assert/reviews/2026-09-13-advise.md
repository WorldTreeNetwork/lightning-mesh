## Blind take

1. Pin the requesting principal to both a registered card's exact `WindowProxy` (`event.source`) and its configured entry origin; `event.origin` alone identifies an origin, not an authorized card.
2. Pin the signed audience to the validated message origin and reuse the v1 nonce grammar and single payload builder; app-supplied audience, timestamps, pubkey, or arbitrary bytes are refused.
3. Pin every response to the captured requesting window with an exact `targetOrigin`, and send nothing if that card has been removed, replaced, or no longer matches the request.
4. Refuse identity messages outside the versioned mini-app envelope, from non-card windows, from opaque (`null`) origins, with malformed nonces/prompts, or while another request for that card is unresolved.
5. Refuse all signing whenever hello.mesh is framed, including silent or previously approved paths; the frame check must precede identity loading, approval lookup, and bridge registration.
6. Consent that counts must be a fresh user action on hello.mesh chrome outside the app frame, name the requesting origin as the authority, and remain bound to the exact pending source/origin/nonce tuple.
7. A remembered approval may authorize only the same normalized origin and fixed assertion shape; it must never become authority for another origin or a general signing primitive.
8. Apply clickjacking protection to every hello.mesh application HTML response and regression-test the captive-portal documents separately so probe discovery, pass-through, and exact success payloads survive.
9. Require abuse-case tests for spoofed origins, sibling cards, stale/navigated windows, duplicate or racing requests, malformed payloads, denial, and framed hello.mesh before this auth bridge ships.
10. Tradeoff: silent `prompt:none` improves embedded continuity but creates ambient correlation/signing; retain it only behind prior per-origin approval and a persistent, trusted hello.mesh identity-sharing indicator with a revoke path.

## Comparison and steelman

The authored design answers most of the blind concerns cleanly. In particular, it composes with `add-mini-app-contract`'s two-part receive check (`event.source === frame.contentWindow` and `event.origin === entryOrigin`), exact-origin sends, cross-origin-only insertion rule, versioned/size-bounded envelope, and prohibition on app code entering the key-holding origin. It also reuses the v1 builder, signer, encoding, verifier, nonce grammar, expiry, error vocabulary, and approvals store. Leading consent with the browser-authenticated origin while demoting the manifest name is the right authority model. The CSP plus an independent runtime frame check is also the correct defense-in-depth shape.

I am steelmanning the intended implementation as a per-card controller that already knows its iframe and entry origin, not as a global message handler that trusts `event.origin` in isolation. I am also treating `prompt:none` as the existing v1 fixed-shape, previously-approved assertion facility—not an arbitrary signing oracle. Under those favorable readings, the remaining gaps are still auth-boundary gaps in the written contract, not stylistic nits.

## Send-back findings

1. **Framed silent signing is not refused.** The delta only forbids rendering approve controls when `window.top !== window` (lines 39–41), and the task says the same for the consent UI and `/assert`. Neither requires the bridge or `/assert` to abort before the `prompt:none` branch reads prior approval and signs. The existing `/assert` implementation performs silent signing before rendering any consent UI, so hiding controls does not close this path. Require a fail-closed top-level check before identity loading, approval lookup, bridge registration, or any call to `signAssertion`, with a test proving a framed, previously-approved `prompt:none` request cannot sign. This matters independently of CSP because `frame-ancestors 'self'` intentionally permits same-origin ancestors and runtime/header coverage can regress.

2. **A response is origin-bound but not yet request-document-bound.** `targetOrigin = entryOrigin` blocks a frame currently at a foreign origin, but the delta never says to post to the exact captured requesting `WindowProxy`, and a `WindowProxy` survives navigation. A sibling card on the same origin is therefore not ruled out by `targetOrigin`; a frame that navigates away and back to the entry origin before approval can also receive a response for an earlier document. Capture the requesting card/window in the pending record and invalidate the request on any iframe `load`, removal, or replacement before approval (or use an equivalently document-bound channel). Tests must cover a same-origin sibling and navigation back to the same origin, not only navigation to `other.mesh`.

3. **Per-card pending limits do not define cross-card consent concurrency.** “At most one open sheet per card” still permits two cards to race a single host consent surface. The artifacts do not specify whether requests are globally serialized, safely queued, or rendered as distinct sheets, nor require the Allow action to remain bound to the displayed source/origin/nonce tuple. This leaves room for state overwrite and origin-confusion at the user gesture. Pin one global pending consent or a concrete safe queue, and test simultaneous requests from different cards.

4. **`prompt:none` needs trusted, accurate ambient disclosure.** Yes, a successful silent request should produce a visible hello.mesh-chrome indicator on that card. The host can truthfully say “Identity shared with `origin`”; it cannot claim the app established a session, so “signed in” is too strong unless the app later confirms that state. The design proposes a badge but neither the delta nor this change's tasks makes it a shipping dependency. Track the shelf-owned pixels explicitly and require the indicator for every successful silent issuance. I would not make a new revoke UI a blocker here because approval revocation is an existing `/assert` lifecycle concern and redesigning v1 is out of scope.

5. **The CSP scope is contradictory.** The delta says hello.mesh “HTML responses” carry `frame-ancestors 'self'`, while the implementation task explicitly excludes captive-portal probe payloads. Keep the exclusion: the probe page holds no key or approval control, is deliberately served at intercepted OS probe origins, and broadening its headers adds compatibility risk without protecting the auth surface. Amend the requirement to say SPA/static hello.mesh application HTML, explicitly exclude `PORTAL_HTML` and byte-exact probe success bodies, and test both CSP presence on application HTML and unchanged captive-portal/pass-through behavior.

## Answers to the flagged questions

- **Captive portal:** no; leave `PORTAL_HTML` and probe success responses outside this CSP change, but make that exclusion explicit and regression-tested.
- **Silent indicator:** yes; require a trusted card-header “Identity shared with `<origin>`” state after successful `prompt:none`, owned by the shelf change but tracked as a dependency of this auth feature.

## Disposition

Send back for the five contract/test closures above. The core transport choice is sound and should remain: this review does not ask for a new token, a redesign of `/assert` v1, or app access to key material.
