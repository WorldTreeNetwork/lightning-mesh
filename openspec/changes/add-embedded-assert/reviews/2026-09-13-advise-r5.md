## Blind take

1. Pin the cooldown subject to the stable `ServiceBookV2` map key (the non-reserved `.mesh` service name), because that is the directory identity under which an embeddable app is presented.
2. An app-record tuple containing `name`, `protocol`, `ip`, and `port` separates different service names, and one-card-per-app prevents duplicate cards for one currently rendered record, so ordinary cross-app starvation is blocked.
3. Refuse that tuple as churn-proof by itself: the same publisher may refresh the same name with a different IP, port, or protocol, producing a fresh tuple that misses the old cooldown.
4. The amendment closes app escape only if cooldown state is migrated across record refreshes or, more simply, lookup is keyed by stable service name regardless of mutable endpoint fields; one-card-per-app alone cannot do this.
5. Distinct service names must never share cooldown even if they resolve to the same endpoint or origin; one ServiceBook key names one presented app, so self-throttling within that name is the intended denial boundary.
6. Pin the outcome table to cover success/Allow, Deny, dismiss, expiry, app-driven reload/navigation/replacement, visitor close or host removal, busy slot, active cooldown, both `prompt: none` failure modes, and malformed input.
7. Each ending needs exactly one response kind, one cooldown decision, and one pending-record/global-slot retirement rule; app-driven teardown must remain distinguishable from visitor/host teardown.
8. `access_denied` for explicit Deny, `interaction_required` for non-consent or unavailable-interaction endings, and `invalid_request` for malformed input are consistent only if no broader response clause overlaps those rows.
9. Refuse any remaining claim that the transferred port proves document ownership or cannot survive replacement; the authenticated window event identifies the requester, while the port is only a requester-designated and deliberately delegable response capability.
10. Tradeoff: a name-keyed cooldown may briefly throttle a legitimate endpoint republish under the same app name, but it preserves the abuse boundary across publisher-controlled address/port churn instead of making cooldown optional to the requester.

The ten lines above were persisted before opening the amended delta,
`design.md`, `proposal.md`, or `tasks.md`. They are concerns the amendment
must answer, not a competing design.

## Comparison and steelman

The amendment makes two substantial repairs. Its table assigns Deny,
dismissal, expiry, reload, host removal, contention, cooldown, silent failure,
and malformed input one named result and one cooldown effect
([delta lines 41–55](../specs/mesh-mini-apps/spec.md#L41)); the response rule
now defers to that table ([lines 228–240](../specs/mesh-mini-apps/spec.md#L228)).
The capability account is also precise: the request designates a delegable,
one-way response endpoint, not document-owned proof
([delta lines 19–27](../specs/mesh-mini-apps/spec.md#L19);
[design lines 8–9](../design.md#L8)).

The strongest case for the new cooldown model is that including the service
name in the tuple separates independently named apps even when their origins
or endpoints otherwise coincide, while one-card-per-record prevents duplicate
UI for one unchanged directory value. That is enough against the round-4
same-origin-sibling example if records never change. The accepted directory
model does permit those values to change, however, so the stronger churn claim
does not follow.

## Round-4 closure audit

1. **Origin-keyed cross-card denial — cross-app half closed, churn half still
   open.** The cooldown now includes the service name rather than bare origin,
   and explicitly promises isolation between apps
   ([delta lines 67–79](../specs/mesh-mini-apps/spec.md#L67)). The one-card rule
   also prevents duplicate cards for the exact same tuple
   ([lines 283–296](../specs/mesh-mini-apps/spec.md#L283)). But IP, port and
   protocol are mutable fields of a `ServiceEntryV2`, while the stable service
   name is its `ServiceBookV2` map key
   ([service lines 63–73, 79–98](../../../../crates/mjolnir-mesh/src/crdt/service.rs#L63)).
   Republishing the same name with a changed endpoint therefore creates a new
   cooldown key. The requirement neither carries cooldown state forward nor
   reconciles an already inserted old-record card, so app-driven record churn
   still evades cooldown.
2. **No-key dismissal and teardown errors — closed as an error mapping.** The
   table gives dismissal (with or without a key), expiry, app reload, and
   visitor/host removal exactly `interaction_required`, while explicit Deny
   alone gets `access_denied` ([delta lines 44–55](../specs/mesh-mini-apps/spec.md#L44)).
   The no-key scenario agrees ([lines 222–226](../specs/mesh-mini-apps/spec.md#L222)),
   and the response requirement contains no competing blanket error rule
   ([lines 228–240](../specs/mesh-mini-apps/spec.md#L228)). A new scope
   contradiction in the table's universal preamble is recorded below.
3. **Stale document-proof text — closed.** The threat rows now say a
   replacement does not inherit the endpoint absent deliberate delegation,
   expressly reject timing/origin checks as document proof, and state that the
   port proves no holder context ([design lines 8–9](../design.md#L8)). The
   detailed explanation repeats the same requester-designated capability
   boundary ([design lines 41–51](../design.md#L41)).

## Send-back findings

1. **The app-record key is mutable and therefore app-escapable.** A same-owner
   service refresh may retain the one authoritative `.mesh` name while changing
   IP, port or protocol; all three are inside the cooldown key. The publisher
   can thus republish `keyed` at a new port or IP and immediately request again
   under a fresh tuple. One-card-*per-tuple* does not cure this and may permit
   an old inserted card plus the refreshed record's card unless refresh
   reconciliation is separately specified. Consequently the design's claims
   that re-creating cards cannot escape cooldown and that two same-origin cards
   “can't happen” are not established
   ([design lines 10, 18–19](../design.md#L10)). Key cooldown by the stable
   service-name identity, or normatively migrate it across record revisions,
   define what happens to an already open card on republish, and test active
   cooldown across both IP and port changes. The accepted embedding boundary
   makes service name the available stable subject: only non-reserved name-host
   origins embed, while IP-literal entries do not
   ([accepted lines 107–123](../../add-mini-app-contract/specs/mesh-mini-apps/spec.md#L107)).
2. **“Every request” has both one response and no response.** The table
   preamble requires every request to end with one outcome sent on its port
   ([delta lines 41–42](../specs/mesh-mini-apps/spec.md#L41)), but a request
   without exactly one port and a same-card duplicate are both expressly
   dropped without a response
   ([lines 14–17, 60–65](../specs/mesh-mini-apps/spec.md#L14)); their scenarios
   repeat that behavior ([lines 93–109](../specs/mesh-mini-apps/spec.md#L93)).
   The table has no row for either intentional drop. Scope the one-outcome law
   to a precisely defined response-eligible request (and state the exclusions),
   or include every request ending in the table. Then make proposal/design use
   the same scope so “every ending” is not an overclaim.

## Disposition

Send back for a stable cooldown identity across record republish and one
consistent definition of which requests receive a terminal outcome. The
round-4 no-key/teardown error conflict and stale document-proof rationale are
closed.
