## Independent take (blind)

Written from `proposal.md` Why/What, the household-authority and
mesh-admin-capabilities change specs, `crdt/leased_name.rs`, and the 71x
ingest/apply comments in `mjolnir-meshd.rs` and `mjolnir-hello/src/routes.rs`.
I had not opened `design.md`, `tasks.md` or the change spec yet.

1. Pin a closed verdict type: `OwnerVerified{issuer, epoch}`, `NodeVouched{node}`, or `Refused{reason}`. Nothing can convert `NodeVouched` into `OwnerVerified`. The type, and not a doc note, should make it impossible to read an observation as a signature.
2. Pin that owner-signed bytes come from the mesh-admin-capabilities encoder with a record-kind domain tag. The verifier re-encodes from parsed fields and never trusts carried preimage bytes.
3. Pin replay against a node that never saw the original. Authority epoch, a per-issuer monotone sequence and an expiry go inside the signed bytes. A cold node refuses an old record because it is expired or superseded by the head it holds, not because of a local seen-set.
4. Pin that the trusted issuer set comes only from the verified authority head and never from the record. Decide whether withdrawal retroactively disqualifies earlier records for control use. I would make withdrawal retroactive.
5. Pin forked-head handling. Two owner-valid heads at one epoch fail closed for every dependent decision until the owner resolves them. No HLC or last-writer-wins tiebreak.
6. Pin that unreadable freshness state means deny plus a reported reason. Refuse the existing `load_leased_names` pattern, which falls back to an empty book on decode error, for anything under this contract.
7. Refuse to call leased names owner-signed after a mesh-wide signature re-check. The v1 preimage covers only `challenge/name/port`. `ip`, `scheme`, `app`, `first_claimed_at` and `renewed_at` are unsigned, and challenge freshness is known only to the ingesting hello. A relay can replay the sig with a fresh `renewed_at` to hold a name forever, or backdate `first_claimed_at` to win a reclaim. Leased names stay node-vouched and must never be admin input.
8. Pin who vouches. A gossip message is authenticated only to the immediate iroh peer, not the originator. "Node-vouched by X" must mean X signed it or X is the delivering peer, not an unauthenticated field.
9. Refuse a second encoder, alias resolution records, and writing heads. Those belong to ai0.1, `add-https-aliases` and `add-household-owner-claim`.
10. Tradeoff: failing closed on a fork or lost freshness turns a corrupted or isolated node admin-dark until the owner reauthorizes. That is acceptable only if the data plane and read-only diagnostics stay up and the denial is shown honestly.

The strongest case for the author: this is an instrument slice. Time
evidence (`time-evidence.md`), the `HighWaterFloor` and the replay ledger
(`b6j.2`) already belong to ai0.1, so this change should only verify
records and leave freshness to the engine. I accept that for the
request-replay ledger and for clock authentication. It does not cover
B1–B2. `time-evidence.md` derives `unix_seconds` and
`authority_verified_at` from "newest verified authority/revocation record
time". It does not say what a verified authority record is or when its
time counts. This change produces those records, and its own spec claims
"A node that has not seen a withdrawal SHALL deny … once the household
stale-authority maximum has elapsed." No other change can make that
sentence true, so this change owes the pin.

## Blocking (send-back)

**B1. Freshness has no signed anchor, so the Why's cold-node replay is not met.**
The Why says a replayed record "must fail on a node that never saw the
original". Pin 4 rejects only "an older sequence for the same head, or a
byte-identical record already applied". Both rely on local history, so a
cold or restarted node has nothing to compare against. Worse, re-feeding
the newest legitimate head or issuer record is a stealthy attack. If
receiving it counts as "successful authority verify" and advances
`authority_verified_at`, then a relay that withholds a withdrawal and keeps
replaying the last good record keeps the node "fresh" indefinitely. That
defeats pin 5's stale-authority bound.

Pin the following. Every owner-signed record carries issuer-signed
`issued_at`, and `expires_at` where it applies, inside the canonical
bytes. Freshness (`TimeEvidence.authority_verified_at`) advances only to
the signed `issued_at` of a newly verified record, never to receipt time.
Re-receiving a record that is already applied, or one no newer, leaves
freshness unchanged. Then a cold node rejects an old record by its signed
time against the stale maximum, and silence or replay ages out as pin 5
intends. Add a scenario: "replay of the newest valid record to a node
past the stale maximum does not restore privileged use."

**B2. Sequence scope, duplicate semantics and seam ownership are underspecified.**
- "Per-head sequence" with several owner or issuer keys under one head
  implies one monotone counter across offline signers, which those signers
  cannot coordinate. Pin the scope, for example
  `(house, epoch, signer, record-type, subject)`. Alternatively, say only
  one signer exists per head.
- "Byte-identical record already applied is rejected" has to mean a no-op
  for a *new decision*, without demoting state that is already applied.
  Anti-entropy re-gossips valid records all the time, so the spec wording
  should say exactly that.
- The applied set and high-water marks are part of "freshness state".
  Missing or corrupt means deny. They are never reset to empty, unlike
  `load_leased_names`. The same rule as the `HighWaterFloor` in ai0.1
  applies.
- Name the seam. This verifier's `OwnerVerified` output is the only
  production constructor for the engine's `VerifiedAuthority` and for
  `TimeEvidence.authority_verified_at`. Today `VerifiedAuthority` in
  `crates/mjolnir-admin-capabilities/src/engine.rs` has all-`pub` fields,
  so any caller could hand a node-vouched fact to `authorize`. Without
  this pin, "a vouched fact never satisfies an owner-signed check" is
  policy, not structure.

**B3. Withdrawal is ambiguous about retroactivity and about who can withdraw.**
Pin 5 says withdrawal makes "*later* records from that issuer unusable".
The spec scenario rejects a grant that was issued before the withdrawal and
has not expired. Choose one and state it. My recommendation is that, once
a withdrawal is verified, no record from that issuer authorizes control,
whatever its signing time. Also pin who may sign a withdrawal. Under
household-authority, issuer changes are owner-only, single-use and capped
at 5 minutes. A peer issuer or the withdrawn issuer must not be able to
withdraw, or un-withdraw, another issuer.

**B4. The fork rule has no defined way out.**
"Refused until a single successor exists" is undefined when the owner's
fix names only one branch, because "names one previous head" is required.
After B→D, branch C still exists, and a consumer that saw both still holds
two heads. `add-household-owner-claim` is the only writer and needs a
consumer rule to write against. Pin one of these:
- (a) a successor at a higher epoch that names one branch supersedes every
  sibling at the lower epoch, or
- (b) a resolving successor must name all observed branches. That is a
  multi-parent exception to "one previous head".

Also state that a forked node does not fall back to the common ancestor
for privileged use. Read-only diagnostics and the data plane continue,
per take 10.

## Non-blocking

**N1. The encoder foil is wrong.** The existing encoder is
deterministic CBOR (`minicbor`) with a closed schema and a decode/re-encode
equality gate. It is pinned by `add-mesh-admin-capabilities/codec-profile.md`,
with `REQUEST_DOMAIN = "lightning-admin/request"`. It is not JSON. "Reuse"
should mean the same canonical-CBOR profile and gate, with closed
per-record-type schemas added to the same crate under new domain strings
(for example `lightning-admin/record/<type>`, version 1), plus a
`codec-profile.md` amendment. "Pass a domain tag into the encoder" fits
poorly, because `AdminRequest::encode` has a fixed request schema. The
spec scenario should say "a second canonicalization", not "a second, local
JSON canonicalizer".

**N2. Leased-name comments overclaim, and the voucher identity is unauthenticated.**
The `leased_name.rs` module doc says "a node must not be able to forge a
key-owned claim". `routes.rs` says every node re-verifies the sig, and
bead p43 says "trustless". Even after the planned meshd-side re-verify
lands, the v1 preimage omits `ip`, `scheme`, `app` and both HLCs, so a
relay can extend leases or backdate tenure. Leased names stay node-vouched
however the signature check turns out. The design should say that
explicitly. Then either correct those comments or file a follow-up bead,
so a later p43 task does not "upgrade" them to owner-signed. Separately,
the originating node of a multi-hop `LeasedNamePublish` is not
authenticated. Any UI that shows "vouched by X" should name the delivering
peer or nothing.

**N3. The consumers in the user journey are unwired.** The proposal says
Lightning Admin and meshd owe this check. The tasks build only the
verifier and tests. Either narrow the journey to the library instrument,
or add tasks that name the consumers. Admin is not a workspace member, so
state that it links the same crate and does not reimplement the check in
TypeScript.
