## R5: the renewal sentence is false when an address holds nine

`specs/iroh-dial/spec.md` line 47 says:

> A claim whose endpoint id is already one of the live hints at that same address SHALL still be accepted.

hello counts the live hints at the claimed address whose id differs from the claim's, and refuses at 8 or more (`projection_source_at_cap`, `iroh_dial.rs:242`; called at `routes.rs:731`). A renewal passes only while the address holds 8 live hints or fewer in total. At 9, every renewal from that address counts 8 others and is refused.

The same paragraph makes 9 reachable. Its last sentence says a known id replaces its row "even when the new address already has 8 other live hints", and the scenario "Known id moves onto a full address in the book" ends with 9 live hints at `10.42.2.20`. In that state the sentence before says refuse and this sentence says accept. The code refuses.

I ran it. A scratch crate outside the repo applied eight ids at one address, moved a ninth known id onto it through `apply`, and then asked hello's cap function about the projection. `apply` returned `Updated`, the address held 9, and the cap refused the mover's own renewal and the renewal of each of the other eight. The test passed. Its body is under Evidence so act can lift it.

**Required edit.** Bound the sentence by the count. For example:

> hello SHALL NOT count the claim's own endpoint id, so a renewal by one of at most 8 live hints at that address is accepted. When the address holds 9 or more, which the book's rule allows, hello SHALL refuse every claim for that address until enough hints fade.

The scenario "Renewal at the cap" is already correct for 8 and can stay. A scenario for 9 is not required, but the delta creates the state two scenarios earlier, so I recommend one.

How the state arises in the field: a known id's move has to pass a hello whose projection shows fewer than 8 others at the target. That needs a move and a new id landing in the same 5 s tick, a different gateway's hello with a lagging projection, an unreadable projection, or a member node publishing by gossip. It is narrow. The gate is on the sentence, not on field risk.

## Blind take

Written to this file before I opened the delta, `design.md`, `tasks.md`, or the first review. Inputs were `proposal.md` and the code at `1a55cc7`. Two deviations: I read all of `proposal.md`, not only Why, and the packet's anchors named the four R themes in a line each, so the take was not blind to them.

1. Pin the preimage bytes: `mjolnir-iroh-dial:v1\n<challenge>\n<port>\n<ip>\n<signed_at_ms>`, lowercase hex, unpadded decimal, strict Ed25519 verify.
2. Pin two projection rewrite rules, not one. The sweep rewrites every 5 s tick whether or not anything changed. Gossip receipt rewrites only on insert or update.
3. Pin the receipt check as the whole of `apply`: port, `10.42` host address, encodings, signature, clock window by the receiver's clock, last-writer-wins with a tie keeping the incumbent, then the cap for an id not yet in the book.
4. Pin what gossip does not check: the TCP peer and the challenge's issuance. Only the submitting gateway saw those.
5. Pin fade as 90 s past `signed_at_ms` on each checker's clock, re-checked at lookup, so a projection one tick old never serves a faded record.
6. Pin re-announce: every fourth tick each node republishes its whole live book, including records it learned by gossip. A restart empties the book. Refill is a peer's re-announce or the client's renewal, never disk.
7. Pin the hello cap as its own rule. hello counts other live ids at the claimed address in the projection, for a known id as well as a new one. `apply` caps only a new id. They differ when a known id moves to a full address.
8. Refuse any sentence that makes the cap a hard bound per address. An address move skips it in `apply`, and hello reads a projection that lags the spool by up to one tick.
9. Refuse persistence, a listing, a relay URL, and a name key.
10. Tradeoff: a memory-only book plus whole-book re-announce converges a restarted node in about 20 s with no disk state, and costs nodes × records messages per 20 s. The spec should state the cadence and leave the bound to `mjolnir-mesh-23ks.5`.

## Notes that do not gate

**n1. "A peer's re-announced hint" is narrower than the code.** After a restart any accepted `IrohDialPublish` refills the book, including a peer's first broadcast of a claim it has just ingested. "A hint received from a peer" would be exact. It can ride with the R5 edit.

**n2. "Every fourth tick" is now a SHALL and the tick has no length in the delta.** The first advise said the cadence could stay out as tuning. Stating it is true to the code and I accept it. A retune of the multiple now needs a spec change, and a reader of the folded spec will not learn that a tick is 5 s.

**n3. At nine, the whole address is locked out of renewal.** This is the product side of R5. Every one of the nine is refused at hello until one fades, which takes up to 90 s, and several can fade before the rest get a renewal through. It heals itself and the record is a hint. It comes from keeping both cap rules as shipped. It belongs with `mjolnir-mesh-23ks.5` or its own bead. I did not file one: my write paths are this file and `tasks.md`.

**n4. The packet's node id is not a bead.** `bd show mjolnir-mesh-23ks.1-advise-r2` finds nothing. The epic's children are `23ks.1` to `23ks.5`.

```rust
#[test]
fn renewal_is_refused_at_hello_when_the_address_holds_nine() {
    let now = 1_700_000_000_000;
    let full = Ipv4Addr::new(10, 42, 2, 20);
    let elsewhere = Ipv4Addr::new(10, 42, 2, 10);
    let mut book = IrohDialBook::new();
    for seed in 1..=8u8 {
        assert_eq!(apply_iroh_dial(&mut book, claim(seed, full, now), now), DialOutcome::Inserted);
    }
    assert_eq!(apply_iroh_dial(&mut book, claim(9, elsewhere, now), now), DialOutcome::Inserted);
    let moved = claim(9, full, now + 1_000);
    assert_eq!(apply_iroh_dial(&mut book, moved.clone(), now + 1_000), DialOutcome::Updated);
    assert_eq!(book.values().filter(|e| e.ip == full).count(), 9);

    let projection = iroh_dial_projection_json(&book, now + 1_000);
    assert!(iroh_dial_source_at_cap(projection.as_bytes(), full, &moved.endpoint_id, now + 2_000));
    for seed in 1..=8u8 {
        let id = claim(seed, full, now).endpoint_id;
        assert!(iroh_dial_source_at_cap(projection.as_bytes(), full, &id, now + 2_000));
    }
}
```

`claim(seed, ip, at)` signs `iroh_dial_signing_message` with `SigningKey::from_bytes(&[seed; 32])`, port 4000, and a 64-character challenge, the same shape as `signed` in `iroh_dial.rs:345`.
