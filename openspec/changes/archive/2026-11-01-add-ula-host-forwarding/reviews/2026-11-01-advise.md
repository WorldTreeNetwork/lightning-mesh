## Blind independent take

Written before opening design.md or tasks.md, from the proposal's Why, the living identity-derived-ula spec, and the cited Babel/ULA code.

1. Pin reachability of each router's house `/128`; the house `/48` names an address space, not an on-link segment.
2. Pin identical policy in both Babel renderers, with explicit host allows before the unconditional ULA in/out denies.
3. Refuse broad house `/48` or `/64` acceptance or origination that also admits unowned hosts or changes kernel on-link behavior.
4. Pin local origination to the usable, currently configured router host; tentative, failed, missing, and stale assignment must fail closed.
5. Require an explicit source of eligible remote host identities and distinguish a route allowlist from authenticated ownership or reachability.
6. Pin replacement and withdrawal behavior when the guild, local address usability, or eligible peer set changes, including a process restart.
7. Refuse accidental export of legacy ULAs, stock OpenWrt ULAs, transport addresses, foreign houses, or app subnet hosts in this router-only step.
8. Preserve existing IPv4 gateway, client subnet, mobility, and interface-metric behavior while adding the host exception.
9. Require real babeld evidence for exact `/128` origination and forwarding, with first-match ordering and no unproven ge/le qualifiers.
10. Tradeoff: exact host lists keep the exception narrow but can cause config/restart churn; the design must make that lifecycle cost explicit.

## Comparison and steelman

The `/48 eq 128` filter answers the covering-prefix concern: matching host routes inside a prefix does not install that covering prefix. I withdraw the blind take's preference for enumerating eligible remote hosts. A stable prefix-length filter avoids peer-driven config restarts, and this node need not introduce authenticated route ownership. It admits any advertised `/128` within the house, including subnet 1; that is distinct from originating an app route or admitting a foreign house. The exact local redistribution rule, placed before the local deny, keeps origination narrow. Keep the trust limitation explicit rather than adding an unrelated membership mechanism.

The spike is useful evidence and remains unchanged. Its log shows the exact-host trial's successful ping, the absent stock route, the random destination failing, and `eq128_installed=1` in the second trial. Its finding correctly distinguishes babeld 1.14 runtime evidence from the 1.13 source inspection and identifies the veth substitution. I accept those observations and the dual-assign argument. They do not establish the product overlay's IPv6 unicast forwarding. Carry the version limitation into implementation validation; the reader did not rerun the spike or inspect upstream 1.13 source independently.

## Owed before acceptance

### R1 — Blocking: the existing overlay drops house-addressed packets

`design.md:17` relies on `mjolnir0` already carrying Babel for IPv4. In `crates/mjolnir-mesh/src/bin/mjolnir-meshd.rs:8349`, `OverlayRouter::next_hop` accepts IPv6 only when the destination starts with `fe80`; a house `fd…` destination returns `None`. `overlay_reader` drops unresolved unicast (`:8406`). `fib_mirror` polls only `ip -4 route show` (`:8424`). Installing an IPv6 host route in the kernel therefore sends the packet into a TUN whose userspace demultiplexer cannot select its connection. A veth bypasses this code entirely.

Amend the design and work contract to cover IPv6 host-route next-hop resolution through the existing Iroh connections, including route withdrawal, or identify an explicit prerequisite that supplies it. Preserve the IPv4 underlay and link-local next-hop invariants. Add acceptance that exercises the actual overlay resolver and packet path for two house hosts, including the return path and an unknown destination. Renderer string tests alone cannot satisfy the stated cross-site journey. This does not require changing the spike finding; a focused overlay spike is an option for the missing evidence.

### R2 — High: the qualifier ban conflicts with gateway preservation

`tasks.md:5` says not to emit `ge` or `le`, and the delta scenario “House host routes are allowed and the rest of fc00 stays denied” requires each rendered config to contain neither. Both existing renderers deliberately emit `redistribute ip 0.0.0.0/0 le 0 metric 128` for a gateway (`crates/mjolnir-mesh/src/babel/config.rs:202` and `:309`). The exact-default restriction is existing behavior, not the failing host-prefix qualifier form. A literal implementation of the new requirement would change the gateway export or fail a valid gateway configuration.

Scope the prohibition to the new house rules in design, tasks, and the delta scenario. Require gateway-on and gateway-off regression coverage for both renderers, preserving the existing default-route line and its ordering. Do not remove `le 0` to satisfy this new test.

### R3 — Medium: define what “known” means and connect it to reconciliation

The proposal uses “guild id is configured,” while the design, task, and delta use “house router `/128` is known.” Neither Babel reconciler currently supplies house state to its renderer (`mjolnir-meshd.rs:7969` and `:8582`); assignment and usability are maintained separately. Pure renderer tests could pass while startup remains deny-only or a changed/removed guild retains old allows.

Pin the renderer input's source and eligibility: a derived desired address versus the currently usable address, with consistent semantics for missing/malformed guild files and tentative/DAD-failed addresses. State how both reconciler loops refresh that input and remove old-house permissions after a guild change/removal or restart, using the existing config-change restart path. Add focused integration coverage for those transitions. This is contract clarification, not a request for a second address-ownership state machine.
