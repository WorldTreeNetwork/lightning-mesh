## Blind take

1. Pin `identity.request` to the registered card's exact `WindowProxy` and entry origin, require exactly one transferred response port, and retain the accepted envelope's serialization and 16-KiB checks.
2. Describe the peer endpoint honestly as a requester-designated, delegable capability; refuse any claim that the host proves which document created or retains it.
3. Make the port strictly host-to-app: install no command path, ignore inbound port traffic, send at most one terminal response, and close both the port and pending record together.
4. Bind audience to the registered entry origin and pin audience plus nonce from the authenticated window event; later port or bridge traffic must not mutate either value.
5. Store an absolute host deadline; at or after it expiry wins, while an earlier Allow must atomically claim the still-live record before any payload build or signing.
6. Require every terminal path to claim or retire the same pending record exactly once, release the global slot, and define whether it starts cooldown without allowing a stale timer or click to respond twice.
7. Refuse origin-only cooldown unless duplicate-origin cards are impossible: otherwise one sibling card can starve another, and a hostile app on a shared host can lock out a distinct app with the same origin.
8. Allow cooldown reset only through a direct trusted shelf gesture for the affected card; iframe reload, self-close, navigation, bridge messages, teardown, or app-triggered reopen must not reset it.
9. Pin terminal error semantics consistently: expiry, contention, cooldown and silent/no-key paths may use `interaction_required`, while an explicit consent Deny or dismiss must not also be specified as `access_denied` elsewhere under the same precondition.
10. Tradeoff: a one-shot response port closes involuntary navigation delivery, but deliberate delegation remains possible and finer-grained cooldown keys cost state complexity to avoid cross-card denial coupling.

The ten lines above were persisted before opening the amended delta, `design.md`,
`proposal.md`, or `tasks.md`. They are concerns the amendment must answer, not a
competing design.

## Comparison and steelman

The amendment keeps the right transport. The authenticated outer window event
selects a requester-designated response capability; the host never treats the
port as proof of endpoint ownership, never receives commands on it, emits at most
one terminal response, and closes it. That closes involuntary replacement
delivery without inventing a new assertion format. The deadline model is also
now deterministic: correctness depends on a monotonic absolute deadline and an
atomic claim, not callback ordering. Those are substantive round-3 fixes.

The contract reconciliation is careful. The accepted bridge's source, origin,
unknown-type, serialization, UTF-8 size, exact `targetOrigin`, four original v1
types, and all six original scenarios remain present. The only textual changes
to the old rules qualify them as *window* messages and reformat the type list so
the port-carried response can be the sole exception; the two identity types and
two identity scenarios are additions. No accepted clause or scenario was
dropped.

## Round-3 closure audit

1. **Capability provenance — closed in the normative delta and proposal, but
   contradicted by stale design text.** The delta expressly disclaims endpoint
   ownership proof and permits deliberate delegation
   ([delta lines 19–27](../specs/mesh-mini-apps/spec.md#L19)); the proposal says
   the same ([proposal lines 22–28](../proposal.md#L22)). But the threat table
   still says “a port doesn't survive that document” and calls it a
   “document-owned port” that is proof
   ([design lines 8–9](../design.md#L8)), contradicting the accurate explanation
   later in that same design ([lines 40–50](../design.md#L40)). The round-3
   finding is therefore not closed across the change's architecture record.
2. **Strictly one-way port — closed.** All input is fixed on the authenticated
   window event ([delta lines 5–17](../specs/mesh-mini-apps/spec.md#L5)); the host
   neither starts, listens to, nor interprets the port, sends at most one
   terminal response, then closes it ([lines 19–27](../specs/mesh-mini-apps/spec.md#L19)).
   The forged-follow-up scenario pins non-mutation and one response
   ([lines 82–86](../specs/mesh-mini-apps/spec.md#L82)).
3. **Expiry/click ordering and trusted reset boundary — closed as mechanics.**
   The record stores a monotonic absolute deadline, every request and decision
   checks it, at/after expiry wins, and pre-deadline Allow atomically claims
   before signing ([delta lines 29–39](../specs/mesh-mini-apps/spec.md#L29)).
   Trusted shelf gestures and the forbidden app-driven reset paths are explicit
   ([lines 53–62](../specs/mesh-mini-apps/spec.md#L53)), with delayed-timer,
   near-deadline and reset regressions
   ([lines 106–128](../specs/mesh-mini-apps/spec.md#L106)). The *subject* of that
   cooldown introduces a separate denial problem below.
4. **Accepted Bridge envelope reconciliation — closed.** The MODIFIED block
   ([delta lines 249–326](../specs/mesh-mini-apps/spec.md#L249)) is a faithful
   superset of the accepted block
   ([accepted lines 155–206](../../add-mini-app-contract/specs/mesh-mini-apps/spec.md#L155)).
   Every original rule and scenario survives; `identity.request` remains a
   source/origin/serialization/size-checked window message, exact
   `targetOrigin` remains mandatory for window sends, and only
   `identity.response` uses the one-shot port.

## Send-back findings

1. **Origin-keyed cooldown creates the cross-card denial lever the bounded
   lifecycle is meant to prevent.** The delta explicitly permits two cards from
   the same origin ([lines 217–221](../specs/mesh-mini-apps/spec.md#L217)), yet one
   card's deny, dismiss, or unattended expiry cools down *every* card from that
   origin ([lines 53–58](../specs/mesh-mini-apps/spec.md#L53)). Thus a hostile card
   can periodically expire requests and suppress a distinct sibling card; two
   path-based apps sharing one host become one denial domain. Reset is coupled
   too: “that app's” open control is singular, while the state belongs to the
   origin ([lines 58–62](../specs/mesh-mini-apps/spec.md#L58)). This also
   contradicts the proposal's “per-card cooldown”
   ([proposal line 33](../proposal.md#L33)) and the design's per-card threat answer
   ([design line 18](../design.md#L18)). Choose and specify a stable cooldown
   subject that cannot be churned by an app and does not let one separately
   presented card throttle another, then test same-origin siblings/shared-host
   apps.
2. **No-key dismissal has two incompatible terminal errors.** The no-key
   scenario requires dismissal to return `interaction_required`
   ([delta lines 187–191](../specs/mesh-mini-apps/spec.md#L187)), matching the
   proposal ([proposal lines 63–65](../proposal.md#L63)). The response requirement
   unconditionally says deny *or dismiss* returns `access_denied`
   ([delta lines 193–204](../specs/mesh-mini-apps/spec.md#L193)). These are the
   same `prompt: consent` dismissal under the no-key precondition, so an
   implementation cannot satisfy both. Scope the rules so every terminal state
   has one error. While doing so, name the currently unspecified error for the
   required terminal response on iframe reload/removal/replacement
   ([lines 41–45](../specs/mesh-mini-apps/spec.md#L41)).
3. **The design still contains the rejected document-proof rationale.** Its
   accurate capability discussion cannot coexist with the threat table's claim
   that a port “doesn't survive” the requester and that a “document-owned port”
   is proof ([design lines 8–9](../design.md#L8)). A port endpoint may be
   deliberately transferred out and survive; what a replacement does not gain
   is the peer endpoint *absent delegation*. Align the table with the normative
   capability boundary so a future implementer does not rebuild the
   unenforceable invariant.

## Disposition

Send back for a non-starving cooldown subject, one unambiguous terminal-error
mapping, and removal of the stale document-provenance claim. The one-way port,
absolute-deadline/atomic-claim lifecycle, trusted-gesture reset boundary, and
MODIFIED Bridge-envelope superset are otherwise ready.
