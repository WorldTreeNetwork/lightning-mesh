## Blind take

1. Pin cooldown identity to the stable `ServiceBookV2` service-name key alone; IP, port, protocol, entry revision, and card instance are publisher-controlled mutable attributes.
2. Pin cooldown state outside the live card and live directory record so unpublish, tombstone, and same-owner re-create of the same name cannot reset it.
3. Distinct service names must have independent cooldown and pending state even when they share an owner, origin, IP, port, or response endpoint, preventing starvation across names.
4. A protocol-or-port republish changes the embedded entry origin and must retire the old card and its pending request before any replacement card can become authoritative.
5. Refuse silent retirement: closing an old-origin card with a response-eligible pending request must produce exactly one terminal response and start the same name's cooldown.
6. An IP-only refresh that leaves the browser-facing name origin unchanged may keep the card, but it must not mint a second card, pending slot, or cooldown identity.
7. Publisher-triggered republish can cancel its own visitor's prompt, but that lever is acceptable only if it cannot affect another service name or reset its own cooldown.
8. Duplicate suppression while pending must be keyed by the same service name as the one-card and cooldown rules, not by origin, endpoint tuple, event source, or port identity.
9. Define response eligibility before the outcome table: window/source checks passed, exactly one port transferred, and no same-name request already pending; all other requests are silent drops with no state mutation.
10. Tradeoff: name-stable cooldown may survive legitimate unpublish/re-create and delay a corrected app, but that bounded self-denial is the cost of making publisher-controlled churn unable to erase throttling.

The ten lines above were persisted before opening the amended delta,
`design.md`, `proposal.md`, or `tasks.md`. They are concerns the amendment
must answer, not a competing design.

## Comparison and steelman

The amendment adopts the strongest version of the blind-pass identity rule.
Cooldown is keyed only by the `ServiceBookV2` service name, expressly excludes
card and mutable endpoint fields, survives same-name republish, and never spans
names ([delta lines 75–90](../specs/mesh-mini-apps/spec.md#L75)). Together with
the closed set of reset events, this also covers unpublish and same-owner
re-create: deletion is not a reset event, and publishing the same map key must
retain its cooldown. The underlying directory makes this coherent because the
name is the map key while IP, port, and protocol are entry fields
([service lines 72–98](../../../../crates/mjolnir-mesh/src/crdt/service.rs#L72));
tombstones retain the name's ownership boundary across unpublish/re-publish
([service lines 100–108](../../../../crates/mjolnir-mesh/src/crdt/service.rs#L100)).

The republish behavior is also defensible against the publisher-lever concern.
A protocol-or-port change closes the old-origin card and gives its pending
request one `interaction_required` outcome that starts cooldown
([delta lines 51–63](../specs/mesh-mini-apps/spec.md#L51),
[lines 294–316](../specs/mesh-mini-apps/spec.md#L294)). The publisher can deny
service to its own prompt, but cannot obtain a token, erase its throttle, occupy
another name's state, or starve another name. An IP-only refresh preserves the
name origin and card, so it creates neither a second requester nor a fresh
cooldown subject ([lines 301–322](../specs/mesh-mini-apps/spec.md#L301)).

The response-law repair is equally direct. Eligibility is defined before the
table, and ineligible requests receive no response, pending mutation, or
cooldown mutation; only eligible requests are promised exactly one outcome
([delta lines 41–49](../specs/mesh-mini-apps/spec.md#L41)). Duplicate handling
is consistent despite the nearby “card” wording: one inserted card exists per
service name, and origin-changing republish closes it before replacement
([lines 68–80](../specs/mesh-mini-apps/spec.md#L68),
[lines 294–304](../specs/mesh-mini-apps/spec.md#L294)). The new ineligible-drop
scenario covers portless, multi-port, and pending same-app duplicates
([lines 324–328](../specs/mesh-mini-apps/spec.md#L324)). Proposal and detailed
design use the same response-eligible boundary
([proposal lines 32–37](../proposal.md#L32),
[design lines 59–68](../design.md#L59)).

## Round-5 closure audit

1. **Mutable app-record cooldown key and lingering old card — closed in the
   normative delta.** Same-name IP, port, protocol, card, and delete/re-create
   churn cannot select a new cooldown subject or invoke a reset. Origin-changing
   republish closes the old card and ends its eligible pending request exactly
   once; IP-only republish keeps the sole card. The amendment tests port churn,
   IP churn, and distinct names ([delta lines 306–322](../specs/mesh-mini-apps/spec.md#L306)).
2. **Universal outcome versus intentional drops — closed.** The definition at
   lines 41–49 scopes the outcome table to response-eligible requests and gives
   every ineligible request the same silent, state-preserving disposition. The
   proposal, design, and scenario now agree.

## Send-back finding

The implementation surfaces still contain two mutually inconsistent lifecycle
instructions inside the exact round-5 repair. The base pending-lifecycle task
still calls for a **per-card cooldown** ([tasks line 11](../tasks.md#L11)), even
though the amended contract requires service-name state that survives card
re-creation and record churn. Following that task literally reintroduces the
escape this round was meant to close. The design threat row also says
“Re-opening an app ends the old request”
([design line 10](../design.md#L10)), while the normative one-card rule says
opening an already open app focuses its existing card and creates no second
iframe ([delta lines 330–334](../specs/mesh-mini-apps/spec.md#L330)); an
origin-changing republish, card close/removal, or iframe reload ends a request,
but a shelf focus does not. Align those two instructions with the amended
service-name/focus behavior so implementation cannot choose the rejected
per-card or re-open-cancels-request semantics.

## Disposition

Send back only for the stale implementation/design instructions above. The two
round-5 findings are closed in the normative delta, and the amendment introduces
no denial primitive across service names.
