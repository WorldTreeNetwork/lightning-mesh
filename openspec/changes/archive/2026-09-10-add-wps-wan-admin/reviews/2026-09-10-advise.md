## Blind take (written before design.md / tasks.md / spec delta)

Sources: proposal Why (as quoted in the packet), living `mjolnir-settings`
spec, ARCHITECTURE.md, `mjolnir-wan-admin`, `rc.wps/00-mjolnir-wan-admin`,
`install-node.sh:71-72`, `mjolnir-apply` 296-318 / 369-397,
`docs/LEARNINGS.md` 2026-09-04 WPS lines.

1. Pin: this is a bootstrap/recovery door, not a management plane. ARCHITECTURE says management is the overlay; the window must never become the way fleet ops are done. `LIGHTNING_FLEET_SSH` naming WPS-armed WAN addrs is already leaning on it; the spec must say "out-of-band, physical presence, fallback only".
2. Pin: nft-only, never `0.0.0.0/0`, never UCI `firewall` — the code does this (`cmd_arm` refuses to open when zero prefixes; `COMMENT` handles are the only persistence). `ap3000` leftover `Allow-SSH-WAN` is the anti-pattern the spec must name and forbid.
3. Pin: the `rc.wps` hook exits 0 before `40-wps_ap`/`50-wps_sta`, so stock `wps_pbc` never runs on the open client AP. That is a claim about OpenWrt 25.12 `/etc/rc.button/wps` loop semantics ("break on first success") and must be a SHALL with a field scenario, not a code comment.
4. Refuse: any SHALL that says "keys required". Nothing in this change enforces key-only auth; `dropbear.PasswordAuth=off` is explicitly out of scope, and OpenWrt dropbear defaults to password auth on. The window is honest only as "TCP/22 reachable from connected prefixes"; the auth story is whatever dropbear already is.
5. Refuse: LED as the operator's truth signal when the window can die under it. LEARNINGS 2026-09-04: `fw4 reload` / `wifi reload` flushes the rule; the sleeper and the blinking WPS LED keep going for the rest of the timeout. `status` says disarmed, LED says armed. Either the sleeper re-asserts, or the spec states plainly that reload closes the window and the LED is not authoritative.
6. Concern: `wan_prefixes` uses the logical iface name for `ip -6 addr show dev`. Works on DSA boards where the port is literally `wan`; silently yields no IPv6 rule where the device is `eth1`. Should use `network_get_device`. Instrument-level, not a design flaw.
7. Concern: "connected prefix" is only a LAN when there is a CPE. A node with WAN on a direct ISP DHCP lease opens TCP/22 to the ISP segment (a /22 of strangers) for 15 minutes. Bounded, but the spec should say the box is "whatever prefix the WAN lease sits in", not "the operator's LAN".
8. Concern: `mjolnir-apply` reloads `firewall` (UCI_CONFIGS) — an apply driven through the WPS window closes the very window it came through. Established SSH survives via conntrack; new connections do not. This interaction must be documented in the spec or the runbook (apply-network-name.sh already warns at line 124).
9. Tradeoff I would accept: no reload-survival. Re-asserting via an fw4 include under `/usr/share/nftables.d` would survive reload but is file-on-disk persistence, which is one step from the `Allow-SSH-WAN` leftover. Toggle-by-press with reload-kills-window is the conservative side; document it and keep it.
10. Acceptance-if_true as worded ("keys required, LuCI/hello stay off WAN") is half-verified by this change: hello binds LAN gateway only and uhttpd is moved to 8080 by apply, but neither the window nor the change touches uhttpd's WAN reachability — it is closed only because fw4 wan input is REJECT and the window is scoped to dport 22. The spec should state that scoping as the SHALL, not the outcome.

## Compare: design.md / tasks.md / spec delta against the take

Steelman first. The design answers pins 2, 3 and 9 outright and the delta
carries them as SHALLs: prefix-only (never `0.0.0.0/0` or `::/0`), no UCI,
`fw4 reload` and reboot drop the window, hook exits 0 before `40-wps_ap`,
keys merged not clobbered, reset button untouched. `cmd_arm` refusing to
open with zero prefixes is the right failure mode and the proposal's
"Empty" journey states it. The design picked the conservative side of the
reload tradeoff (take 9) and says so. Field task on wr3000s-a is checked.
Architecture is sound: the door is out-of-band, nft-scoped to dport 22 from
the WAN lease's prefixes, and nothing in the change touches the overlay,
uhttpd, or hello. Acceptance `if_true` holds on the substance.

What the author did not answer, in order of weight:

1. **Delta conflicts with the living `mjolnir-settings` spec (fold-blocking, doc-only).**
   The delta says "The window SHALL last 15 minutes" and the scenario says
   "or 15 minutes elapse". `mjolnir-settings` (folded 2026-09-10, after this
   delta was written) says the duration SHALL be `mjolnir.wan_admin.timeout`
   with a 900 fallback, and the code agrees. Two SHALLs disagree on the
   same fact. Reword the delta to "SHALL last `mjolnir.wan_admin.timeout`
   seconds (default 900)". Added as an unchecked task in tasks.md so fold
   does not land a contradiction.

2. **LED is not authoritative after a firewall reload (take 5, instrument).**
   Design #2 accepts that `fw4 reload` drops the rule, but the sleeper and
   the timer-trigger WPS LED run out the rest of the timeout. Operator sees
   a blinking lamp and a refused port; `status` says disarmed; the next
   press re-arms (toggle sees no rule). Not a security hole: the failure is
   closed. It is an honesty gap between the lamp and the firewall. Cheapest
   fix is a poll in the sleeper (`armed` every few seconds, disarm LED when
   the rule vanishes). Alternative is a spec scenario stating the LED may
   lag. Filed as a bead; not a send-back.

3. **`mjolnir-apply` closes the door it came through (take 8).**
   `UCI_CONFIGS` includes `firewall`, so an apply driven over the WPS
   window drops the window mid-run. Established SSH survives on conntrack;
   the health-gated detached apply is what makes this safe. The proposal
   mentions reload once; `apply-network-name.sh:124` warns. The living spec
   should carry one scenario so the next operator does not read the drop as
   a rollback. Fold-time note for the folder.

4. **"Keys required" is not enforced by this change (take 4).**
   The delta is honest: it says firewall, not bind, is the gate and never
   claims key-only auth. The proposal's "opening the port without a key is
   still `Permission denied`" is true only if dropbear password auth is off
   or root has no password. `PasswordAuth` is out of scope by decision. The
   packet's acceptance wording "keys required" should be read as "keys
   merged"; the out-of-scope bullet should say which it means ("already
   disabled on this fleet" vs "already enabled").

5. **IPv6 prefix discovery uses the logical iface name (take 6, instrument).**
   `wan_prefixes` runs `ip -6 addr show dev "$ifc"` with the
   `network_find_wan` logical name. Correct on DSA boards where the port is
   literally `wan` (the fleet today); silently yields no IPv6 rule on a
   board whose WAN device is `eth1`. Should be `network_get_device`. Filed
   as a bead.

6. **"Connected prefix" is the ISP segment when there is no CPE (take 7).**
   The delta says "prefixes currently configured on the WAN interface",
   which is the exact truth. The proposal's "someone else's CPE" framing
   is the common case, not the bound. Worth one sentence in the living spec.

7. **Consume-WPS SHALL has no scenario (take 3).** The delta states it;
   the design cites OpenWrt 25.12 `rc.button/wps` break-on-first-success.
   Field task passed, so the claim is validated once. A scenario ("WHEN
   pressed THEN `hostapd_cli wps_get_status` is not active") would keep it
   validated on the next OpenWrt bump.

Take 1 (bootstrap door, not management plane) is covered by ARCHITECTURE
and needs no change here. Take 10 is met: the delta scopes the SHALL to
dport 22 and states LuCI/hello stay closed as the consequence.
