## Blind take (written from Why, living spec, portal.rs:6-16 only)

1. Pin: dismissal, "Just the internet, please", and identity creation are UI-local; none may write routing, firewall, CAPPORT, or pass-endpoint state (spec: dismissal SHALL NOT override).
2. Pin: the welcome surface is reachable and useful with zero identity and zero JS-persisted state; "anonymous" must mean no server-side visitor record either (no cookie/MAC/IP log keyed to a visit).
3. Pin: the copy for local-only vs. online is derived from the same default-route fact CAPPORT uses, never from a dismissal flag.
4. Pin: consent for identity is explicit, separate from browsing, and failure to persist a key (captive mini-browser lacks storage) is surfaced honestly with a regular-browser path.
5. Refuse: any second front door, any gating of /api/* or services behind identity, any "welcome complete" state that changes what the network allows.
6. Refuse: identity wording implying it buys internet or admin rights; Why says it is an invitation only.
7. Refuse: the QR/manual return path depending on mDNS or off-mesh DNS; hello.mesh must be reachable by LAN address fallback (hello binds 10.42.x.1, not overlay).
8. Pin: empty state (nothing published) still teaches how to return; QR content is a stable local URL, no per-visitor token.
9. Gap to check: the Why promises a return path "when the sheet never appears" but the living spec has no requirement for it; the new capability must carry it as its own testable requirement, not by amending captive-portal.
10. Tradeoff: reusing the Services surface avoids a second door but couples visitor copy to resident UI; accept, provided the visitor view is a distinct mode, not a logged-in-gated variant.

## Steelman against my take

- Gap 2 is arguably out of scope: hello already serves plain HTTP, and logging policy is a node-operations concern, not a welcome requirement. Adding a no-visitor-record rule here could over-constrain existing access logs. Fair; but the word "anonymous" in the Why invites exactly that reading, so one sentence is cheaper than ambiguity.
- Gap 8 is covered by the proposal's journey "Empty" state, and a requirement per UI state would bloat the spec. Fair; the test task should still assert it.
- Take 3 is satisfied by the negative form; mandating a positive derivation from the default route would duplicate captive-portal. Agreed, drop as a blocker.
- The design's refusal to settle the URL question is deliberate and keeps the spec implementable on either fleet DNS state. Agreed.

## Verdict rationale: accept

The change keeps the invariant in portal.rs:14-16 and captive-portal's final sentence intact: nothing here writes CAPPORT, probe, or pass state, and task 15 says so. Requirements are testable and scoped away from owner claim, biscuits, and mini-apps. The remaining items are concerns the author must answer during implementation, not reasons to hold it.

## Concerns the author must have answered (non-blocking)

1. **Design open question (return URL):** answer yes, advertise both `http://hello.mesh/` and the node-local LAN gateway address (`10.42.<x>.1`). Per CLAUDE.md hello binds the LAN address, not the overlay `10.254.x`, and hello.mesh DNS is a dependency that can be down. QR should encode the stable local URL with no per-visitor token. Record this in design.md.
2. "Anonymous" should mean the hub creates no server-side visitor record keyed to the visit (no cookie, session, or stored MAC/IP). One sentence in req 1 or design, or an explicit statement that existing access logs are out of scope.
3. Tests (task 7) should include the empty state (nothing published still explains how to return) and a check that dismissal handlers make no call to portal pass or any routing/firewall path.
4. "Just the internet, please" copy must be correct in both route states: with a default route it may say the internet is already available; without one it must say local-only. The label is a UI hazard because it suggests a request that nothing grants.
5. Req 3 "unverified" storage: define how the flow decides unverified (probe vs. user-agent heuristic) so it fails toward the regular-browser path.
6. Tradeoff accepted: reusing the Services surface couples visitor copy to resident UI. Keep the visitor view a distinct mode, not an identity-gated variant.
