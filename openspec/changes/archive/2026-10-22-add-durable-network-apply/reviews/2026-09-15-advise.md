## 1. Blind take (written before reading design/tasks)

Ten things the author must have answered. This is a list of concerns, not a
competing design.

1. **Reboot mid-apply has no recovery today.** `install-node.sh:172` launches
   via `setsid` — survives SSH loss, not a power cycle. If the node reboots
   during the radio bounce, half-applied config persists, `$STAGE/result` is
   never written, and the backup just sits in `/root/mjolnir-stage/backup`
   with nothing to re-run rollback. A boot-time recovery service reading
   durable transaction state is the load-bearing new piece; without it the
   capability's name is unmet.
2. **"Unreadable result" is already ambiguous, and reboot makes it worse.**
   `install-node.sh:181` states an absent result means "this machine can't
   reach the node yet, NOT that the apply failed." A crash/reboot that leaves
   no result is indistinguishable from a transit outage. The design must make
   in-progress vs. committed vs. rolled-back a *durable readable state*, not an
   inference from a missing file.
3. **The `mkdir` lock has no liveness/owner.** `mjolnir-apply:46` locks with
   `mkdir $STAGE/.lock` + `trap EXIT rmdir`. A SIGKILL / power loss never runs
   the trap, so the orphaned `.lock` refuses every future apply — a crash
   bricks the applier. Durable transaction state must own the lock with a
   fencing/liveness check and a defined recovery, not a bare directory.
4. **Rollback claims restoration it never verifies.** `rollback()`
   (`mjolnir-apply:194`) copies backups, reloads wifi, restarts meshd, and
   writes `ROLLED_BACK: previous config restored` — but runs **no** post-restore
   health gate. "Restored" is asserted, not demonstrated (the anchor invariant
   at `mjolnir-apply:33`). The design must re-verify after rollback or stop
   claiming restoration.
5. **Receipts must not launder local health into a client-internet claim.**
   The health gate proves overlay-address re-assertion + a ping to a pre-apply
   `10.254.x` neighbour or L2 peering (`mjolnir-apply:505–542`). That is mesh
   health, never downstream client internet. `committed` and
   `client-internet-demonstrated` must be distinct, separately-measured fields;
   and per the journey, a **local-only** policy must not render a *false
   internet failure* either. No false evidence in either direction.
6. **Revision binding must be a real check-and-commit.** "Apply against the
   observed revision" needs a concrete token (config generation / hash) and an
   atomic compare-then-commit, or a stale preview races a concurrent change and
   commits against a base that already moved.
7. **Re-entrant apply must not snapshot a half-applied state as its baseline.**
   `mjolnir-apply:184–188` overwrites `$BACKUP` each run. A second apply after a
   partial first would capture the broken intermediate as the "restore" target,
   so rollback restores garbage. Durable state must record the *true
   pre-transaction* baseline and survive retries; retention of old
   transactions/receipts needs a policy.
8. **One transaction owner per node, reconnect-by-ID.** Multi-writer safety is
   claimed via "retrieve the same transaction by ID rather than resubmit." The
   `mkdir` lock gives mutual exclusion but no identity, no fencing token, no
   reconnect handshake. The contract must define how a returning controller
   re-binds and how a second controller is refused without deadlocking on an
   orphaned lock.
9. **Resume-forward vs. restore-on-reboot is a safety decision, not a detail.**
   A half-applied radio change that dropped the mesh: on reboot, does recovery
   re-apply forward or roll back? Either default can strand a house. The design
   must pick one, justify it, and bound retries so recovery cannot loop.
10. **Refuse: a unit-tested model is not OpenWrt completion.** The proposal
    itself scopes implementation to the local helper + test adapter with no live
    writes; reboot-survival and radio re-apply are `z3th`/`lpv`. The advisory
    refuses any acceptance criterion that would let a passing state-model test
    count as reboot-recovery-on-hardware. Model-verified ≠ runtime-complete.

**One tradeoff I would flag:** durable transaction journaling on OpenWrt means
fsync'd writes to the same flash (JFFS2) that holds the config being mutated —
durability vs. flash wear, and the recovery service is itself a new failure
mode (a rollback loop can strand the house harder than the crash did). Cheap,
bounded, idempotent state beats a heavy journal here.

## 2. Comparison — steelman against the blind take

The design (`design.md`) and the capability delta
(`specs/network-change-transactions/spec.md`) answer **all ten** blind concerns.
Point by point, treating each as a concern the author had to satisfy:

| 2 | "Unreadable result" ambiguity | Durable readable state machine `prepared→applying→verifying→committed` / `restoring→restored`/`recovery-required`; "reconciled to its committed revision, not rolled back merely because the controller missed the reply" | **Answered.** State is durable and readable, not inferred from a missing file. |

Matches the refusal.** |

Beyond my take, the contract also pins: no distributed all-or-nothing claim
(sequential per-node receipts, explicit partial completion); a target-owned
**monotonic-within-one-boot** deadline where reboot invalidates a pending
confirmation and takes the recovery path rather than a fresh full timeout;
secrets excluded from public plans/hashes/logs/receipts with the digest not
made a guessing oracle; and a red-first test list that enumerates crash at each
journal transition, partial snapshot, full/unwritable storage, corrupt journal,
and local-only false-positive internet evidence. This is an honest
instrument-level contract; I did not have to relax my take to accept it.

## 3. Acceptance criterion (contrast) — checked

- **if_true holds:** *Controller loss and restart cannot create false
  committed/restored claims or local-only client-internet claims.* Controller
  loss does not cancel target recovery (delta, *Lost controller* scenario);
  `committed` requires a durable commit record gated on the plan's required
  health checks; `restored` requires its own post-restore verification, else
  `recovery-required`; local probes can never establish downstream internet, so
  a local-only node reports `committed/local-only` or
  `committed/client-internet-unknown`, never "house has internet".
- **if_false not reached:** I probed for a concrete crash/race that bypasses the
  snapshot/revision/verification guarantees to emit a *false* claim and did not
  find one **within the contract as written**. The closest is the window
  between a health-pass and the durable `committed` record: a crash there is
  treated as uncommitted and rolled back + re-verified — that costs a good
  apply (availability), but it produces a *truthful* `restored`/`recovery-
  required`, not a false claim, so it does not satisfy `if_false`. Worth a note
  (below), not a send-back.

## 4. Residual notes and act-stage blockers (for the conductor to record in beads)

These are **not** satisfied by this instrument slice and MUST be carried as
gates on the act/implementation packet. They are recorded here for the conductor
to file as beads — no markdown task boxes, per the living spec and packet.

1. **Legacy-helper shared-lock participation is the single most important real
   integration obligation.** `mjolnir-apply` and the root-SSH maintenance path
   are explicitly preserved. Until the legacy helper *participates in the same
   node-wide lock and revision recheck*, a legacy apply concurrent with a
   transaction-manager apply is an unguarded race that the new guarantees do not
   cover. The design names this ("never silently route production radio updates
   through an untested wrapper"; "shared-lock participation … must land and pass
   focused integration tests"); it must be verified, not assumed.
2. **Snapshot/restore allowlist must provably cover the full mutation surface.**
   Today's helper touches far more than four UCI files (wpad package variants,
   `/etc/init.d/*`, dropbear `authorized_keys`, `uhttpd`, hotplug, `mjolnir-*`
   binaries). If a plan can mutate a path the snapshot allowlist omits,
   restoration is incomplete — caught only by the post-restore verification
   backstop (which would then report `recovery-required`). The allowlist-vs-
   mutation-surface coverage is an integration proof owed at act.
3. **Commit-record atomicity window** (health-pass → durable `committed`) should
   be explicitly ordered and documented so the lost-good-apply cost is a
   conscious choice, not an accident.
4. **On-disk format, storage limits, and implementation language remain
   unpinned** by design intent ("Pin … in the act packet"). Flash-wear on JFFS2
   for per-transaction fsync'd journaling is unaddressed and should be bounded
   when those limits are pinned.
5. **Process-death-without-reboot** resolver: recovery is described "after
   process or node restart"; the design should confirm which invocation runs
   recovery when the applier is SIGKILLed but the node stays up (presumably the
   next apply runs recovery-first), so a dead-but-not-rebooted transaction
   cannot silently hold the lock.
6. **Hardware qualification is out of scope and unmet here** — reboot/power-cycle
   and radio re-apply survival are `mjolnir-mesh-z3th`; per-SKU profile + failure
   recovery are `mjolnir-mesh-lpv`. A green state-model + fault-injection suite
   does **not** close `mjolnir-mesh-ai0.5` and must not be reported as durable
   OpenWrt apply.

## 5. Verdict rationale

Accept is a verdict on **design sufficiency to implement safely**, not on any
built or verified behavior. The contract independently reproduces every concern
from the blind pass, picks the safe defaults where a choice was required
(uncommitted→restore, committed→reconcile, uncertain→recovery-required-and-
blocked), refuses to equate a model with runtime completion, and never lets
local evidence stand in for downstream client internet. The acceptance `if_true`
holds; no concrete crash/race that emits a *false* committed/restored/internet
claim survives review of the contract. The residual items in §4 are act-stage
integration obligations and packet-pinning, correctly out of scope for this
instrument slice — they are conditions on the *next* packet, not defects in this
one.
