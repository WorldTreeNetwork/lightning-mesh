## Blind pass — ten-line independent take

1. Pin `app` as optional self-reported metadata outside the v1 signing preimage, with its unsigned trust level stated beside `ip` and `scheme`.
2. Pin one wire shape for name claims: `app: { v: 1, path?: string }`, where absence preserves today's plain-service behavior.
3. Pin one Rust validation contract shared by name-claim ingestion and control-API/CLI publishing, matching the browser `appPath` rules and supported version exactly.
4. Pin rejection before spool creation, lease replacement, or any other persistent mutation, so a bad marker cannot damage the last good claim.
5. Pin backward-compatible deserialization: the added leased-record field is optional/defaulted and records written before this change still parse.
6. Pin canonical directory projection to `app=v1` and optional `path=`, without inventing another marker format or signature ceremony.
7. Pin consumer re-validation in the directory/apps/browser path; publisher validation is prompt feedback and never the security boundary.
8. Refuse any change to `name_claim_signing_message` or any second signing/ownership scheme disguised as app publication.
9. Refuse path-validation drift, CLI-only enforcement, or a flow in which malformed `app`/`path` reaches the spool before a later component rejects it.
10. Tradeoff: unsigned app metadata can be altered by the same node-trust boundary as `ip`/`scheme`, but preserving the deployed ceremony is reasonable if future owner-signed records explicitly absorb it.

## Comparison and steelman

The design substantially matches the independent take. It explicitly keeps the marker outside `name_claim_signing_message`, gives it the same trust posture as `ip` and `scheme`, rejects invalid claims before spooling, defaults the added leased-record field for old records, projects one canonical TXT marker, retains consumer re-validation, and refuses a second signing scheme. Its strongest case is that the marker changes presentation only within the already-derived service origin; postponing authenticity until owner-signed name records land is therefore a coherent compatibility tradeoff rather than an accidental weakening of name ownership.

The proposed shared Rust validator in `mjolnir-mesh`, consumed by both hello and meshd and exercised through cross-language fixtures, is also the right boundary. The CLI remains a convenience over the control API rather than becoming the primary publication model.

## Send-back findings

1. The design and delta add a 256-byte path ceiling, but the cited `contract.ts` `appPath` and the living `App marker on service records` requirement do not contain that rule. Saying the validator is “the same rules” is therefore false at the current contract boundary. Either remove the new ceiling, or explicitly modify the consumer requirement and implementation and include the boundary vectors in both suites. Do not let publish-time validation become stricter than consumer re-validation by accident.
2. The public shape promises an optional `app.path` whose absence means `/`, while the storage shape is written as `AppMarker { v: u8, path: String }` and no default/normalization behavior or omitted-path test is specified. Pin the representation and shared vectors so `{"app":{"v":1}}` is accepted and canonically projects like `/`; also specify that the convenience flag `--app-path` cannot be used without `--app`.

These are preparation defects, not objections to the unsigned-marker architecture. Once the two contracts are reconciled, the planned implementation can satisfy the requested trust, rejection-order, compatibility, and recovery-path constraints without changing the v1 signed preimage.
