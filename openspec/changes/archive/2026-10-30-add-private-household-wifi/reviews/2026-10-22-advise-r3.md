## Blind take (written before opening design.md or tasks.md)

1. Pin the hostapd file shape. `wpa_psk_file` takes lines like
   `00:00:00:00:00:00 <passphrase>`, not the bare passphrase that the
   uplink file holds. `psk2` with no `key` works only through hostapd's
   empty-key-plus-`wpa_psk_file` branch.
2. Pin the reload. A passphrase-only change moves only `mjolnir`, so
   `wifi reload` leaves hostapd alone because `wireless` didn't change.
   Apply and restore must both make hostapd re-read the file. Otherwise
   `secret_generation` is only bookkeeping and "restored" isn't true.
3. Pin fleet order. Each transaction covers one node, but "every house
   node rejects INPUT" is a property of the whole fleet. A guest SSID
   that goes live before the gateway carries the reject is not isolated.
4. Say that the forward deny runs where the guest enters, at the
   source. Then another node's revision can't open it.
5. Pin the SSID cutover. If one SSID name goes from open to `psk2` during
   a leaf-first rollout, phones see an ESS with mixed security.
6. Refuse a guest bridge that is `br-lan` or that roam watches.
   "Guest" in `roam.rs` is a different concept with the same name.
7. Refuse a hello.mesh exception by default, and say what that costs:
   guest-SSID visitors can't reach the hub, even though the household
   spec invites visitors to it.
8. Tradeoff: allow RFC1918 that isn't house space (the ISP LAN and the
   uplink's upstream subnet), or deny all private space. Either is
   defensible. The choice must be written down.
9. Refuse a guest profile on an IPv6 house. That is the right minimal cut.
10. Refuse a builder-invented guest CIDR. The CRDT claim is the source.

## Owed

**R3-1. The INPUT reject on every node is a fleet precondition with no
stated order.**

Steelman: the design lists "every house node rejects INPUT whose source is
in the committed guest-source class" among the conditions that must hold
before the plan may say `isolated`. If the builder had to prove that from
committed state, it would refuse a premature plan. The rule would already
be there.

Why that is not enough:
- `Plan` covers one node. The builder for node N's guest plan sees N's
  config. Neither the spec nor the design says the builder gets every
  house node's committed config, or the house node list, as input. As
  written, the condition can be met by a plan that *states* the reject
  for the fleet while the gateway hasn't committed it.
- This is the case that matters. A guest on a satellite addresses the
  gateway's WAN, `wwan`, or recovery `192.168.1.1`. The satellite
  forwards it, because those addresses are outside the aggregates, and
  the gateway receives it as INPUT. If the gateway still runs the
  previous revision because of a leaf-first rollout or a per-node
  restore, guests reach the gateway's management plane while the
  satellite's receipt says `isolated`.
- The "committed fleet guest plan" has no stated home. Each node needs
  a copy it can read in its own committed `mjolnir`/`firewall`. That
  copy is what makes a node "carry the class".
- A node that joins later (`add-zero-touch-join`) has no reject until
  it carries the class. That is the r1 staleness problem again, moved
  from FORWARD on the guest node to INPUT on every other node.

Owed (two to four sentences plus one test):
- Spec/design: name where each node's committed copy of the guest-source
  class lives. The builder enables a guest `wifi-iface` on node N only
  when the committed configs of every house node, passed in as input,
  already reject INPUT from N's guest CIDR. A node that is missing,
  unreachable, or stale refuses the plan. So the reject commits
  fleet-wide first and the SSID comes last, and a per-node restore of
  the reject can't happen while the SSID is live. Name what a newly
  joined node must carry before guest plans count it.
- Test: a gateway config without the class refuses the satellite's
  guest plan, and the previous revision stays.

**R3-2. The rekey and its restore must reach hostapd.**

Steelman: the uplink gate's contract already includes "reloads inside apply
and restore", and the design calls this gate "the same kind". No live
adapter exists, so nothing can submit a wrong rekey today.

Why that is not enough: the new gate is a new type, and its contract is what
a future adapter will be held to. A revision whose only change is
`mjolnir.secret_generation` looks like a no-op to `wifi reload`. hostapd
keeps serving the old key, so a `committed` receipt would be false. On a
failed rekey, the file is restored on disk while hostapd keeps the new key
in memory, so `restored` would be false too.

Owed (one sentence plus one test):
- Design: the gate's adapter contract says that any revision that
  changes a `wifi-iface`'s `wpa_psk_file` or its `secret_generation`
  makes hostapd re-read the file for that iface, on apply and on restore.
  The plan names those ifaces, as uplink's `UplinkEffect` names
  co-located APs.
- Test: a passphrase-only rebuild names the resident iface for
  reconfigure.

## Notes (not owed)

- design.md says guest input accepts "ND and RA" when IPv6 is enabled. A
  guest on an IPv6 house is refused, so that clause can't apply yet.
  Either drop it or mark it for the later v6 change.
- tasks.md lines 9 and 10 still say "for IPv6 if IPv6 is enabled" and
  "missing IPv6 deny when IPv6 is enabled". The test that matches the
  design is "a guest is refused when IPv6 is enabled or unknown".
- For `lpv`: if the cutover keeps the name `Lightning Mesh`, phones see
  the same SSID with mixed security during a leaf-first rollout.
  `mesh-errand.sh` also depends on joining the client SSID, so it needs
  the passphrase after cutover.

## Verdict

Send-back. Everything that applies to a single node is now right: the
hostapd shape, the aggregate source-side forward deny, the IPv6 cut, the
CRDT-sourced CIDR, keeping guests off roam, and the hello.mesh choice.
R3-1 is the architecture gap. The r2 answer made isolation depend on
the INPUT policy of *other* nodes, but a transaction covers one node.
Without a stated order and a defined input, a guest can reach the
gateway's management addresses while the label says isolated. R3-2 is a
correctness pin on the new gate's contract. Each fits in a few sentences.
I added owed boxes to tasks.md. The fresh-advise box stays open.
