## Blind take (written before opening design.md or tasks.md)

1. The deny has to cover every address a house node will accept as local, not
   just `10.42/16` and `10.254/16`. Some node addresses sit outside those
   aggregates: the gateway's WAN and `wwan` addresses, the recovery
   `192.168.1.1/24`, and a GUA on `wan6`. Linux delivers a packet to any of
   them on whichever interface it arrives. `mesh` is in the `lan` zone
   (input ACCEPT).
2. Pin the guest slice's origin. `10.42/16` `/24`s are claimed through the
   CRDT (`crdt/subnet.rs`, `alloc.rs`). An unclaimed "slice that is not the
   resident `/24`" can collide with another node's lease.
3. Pin who exports the guest slice. babeld redistributes only the node's
   `subnet` and `0/0`. Without an export, the gateway can't return NATed
   replies to a satellite guest.
4. "House ULA" isn't one prefix. Each node has its own random
   `globals.ula_prefix`, and a PD GUA is runtime state, not committed config.
   Pin `fc00::/7`, or a fleet ULA, or refuse guest v6 here.
5. Pin the hostapd shape: `psk2` + `wpa_psk_file` in MAC-prefixed lines, no
   `option key`, and refuse 6 GHz and SAE in v1.
6. Keep the uplink secret parity: snapshot/restore, `secret_generation`, no
   unkeyed hash, and a profile id that doesn't come from the secret.
7. Refuse to state isolation from a peer list. Refuse to label isolation from
   a v4-only deny after v6 turns on.
8. Keep guests out of `roam`. Never put them on `br-lan`, never give them
   proxy_arp.
9. Restate commit scenarios over the planned config, not association.
10. Tradeoff: a destination-prefix deny at the guest's ingress node needs no
    tunnel and no authority, but every other node's addresses must be inside
    that deny set. A source-class deny on every node is robust, but then the
    guest plan touches nodes that serve no guests.

## Steelman, then the owed items

**R1. The aggregate deny leaves house nodes' other addresses open.**

Steelman: the design deliberately narrowed r1's "RFC1918 and recovery ranges"
to the two house aggregates. A guest behind a double-NAT upstream must still
reach the internet, and a peer list goes stale. Both points are right. But
reaching the internet *through* the upstream never needs a guest to address
an RFC1918 or WAN-side host directly.

The failure the current gate passes:
- A guest on a satellite sends to the gateway's WAN address. That is a DHCP
  lease on the upstream LAN, or a public address.
- The address is outside `10.42/16` and `10.254/16`, so the satellite's deny
  lets it through.
- With no babel route to it, the packet follows `0/0` to the gateway.
- The gateway receives it on `mesh`, which is in the `lan` zone
  (`setup-wireless.sh:232-234`, input ACCEPT).
- The weak-host model delivers it to the gateway's own stack: dropbear,
  uhttpd/LuCI.

The same path reaches the recovery `192.168.1.1` when the recovery node is
the wired jump/gateway, a station uplink's `wwan` address, and a gateway GUA
on `wan6`. The spec scenario "a resident address on that gateway is still
denied" holds only for `10.42.x`. The plan would label itself `isolated` while
guests on every satellite can open the gateway's management plane.

The gateway's upstream LAN is a related gap. In a home where the mesh sits
behind the ISP router, that LAN holds resident devices. The design calls it
"internet". The author can keep that choice, but must name it as one.

Owed:
- The spec closes this path. Either answer is acceptable:
  - (a) The ingress deny also covers every address a house node holds outside
    the aggregates (at least the RFC1918, CGNAT, and `fc00::/7` ranges), and
    the spec says how a public WAN or GUA on another node is covered.
  - (b) Every node rejects INPUT from a guest source class except DHCP/DNS on
    its own guest interface. Then (b) needs R2's recognizable guest class, and
    the guest plan becomes a fleet plan.
- One scenario: a guest on a satellite addresses the gateway's WAN (or
  recovery) address, and it is denied.
- Design states whether the upstream LAN is treated as resident or as
  internet.

**R2. The guest slice needs an allocator and an export.**

Steelman: the design keeps the builder pure, and CRDT claims and babel are
meshd's job. That's right for *implementation*. But the spec is the contract,
and its satellite-internet scenario only holds if the slice is claimed
without collision and routed back from the gateway. Today `alloc.rs` claims
`10.42/16` space through `/subnets/{cidr}`. babeld emits only
`redistribute ip <subnet> allow`, then `local deny`, then `deny`.

Owed:
- Spec or design says the guest slice is a CRDT-claimed CIDR, handed to the
  builder as an input, never self-chosen.
- It names who redistributes it. A meshd follow-up bead is acceptable if this
  change records the dependency, so the satellite scenario is checked against
  a stated export.
- If R1 takes option (b), the slice comes from a sub-aggregate every node can
  recognize as guest by source.

**R3. The v6 deny basis has to be something the builder can know.**

Steelman: IPv6 cross-node isn't routed today, because babeld redistributes no
v6. So the v6 path is mostly latent, and "unknown refuses" is already fail
closed. But "the house ULA" is ambiguous: every OpenWrt node has its own
random `globals.ula_prefix`. A guest node's committed config doesn't hold
other nodes' ULAs. A PD GUA isn't in committed config at all. So "IPv6
enabled" is decidable, but the deny prefixes the spec names are not.

Owed (pick one and state it):
- The v6 deny is `fc00::/7` plus a GUA basis the builder can read.
- Or a guest profile on an IPv6-enabled house is refused in this change.

## Notes (not owed)

- Same-node guest-to-guest goes over L2, so the firewall can't stop it.
  `option isolate '1'` on the guest `wifi-iface` is cheap. It isn't required
  by the parent spec.
- If guests get stateful DHCPv6, guest input needs `udp/547` too, not only
  ND/RA.
- For `lpv`: `mesh-errand.sh` and the agent laptop join the client SSID.
  Committing `psk2` there needs the errand path to carry the passphrase, or
  management reachability over the overlay before commit.

## Verdict

**send-back.** The secret handling, commit split, roam exclusion, and
builder gate are ready. The isolation gate is the reason this change exists,
and it can still label a plan `isolated` while satellite guests reach the
gateway's own management addresses (R1). The gate also rests on a guest
prefix with no named allocator or export (R2), and on v6 prefixes the
builder can't read (R3). These are text changes to `spec.md`/`design.md`,
not code.
