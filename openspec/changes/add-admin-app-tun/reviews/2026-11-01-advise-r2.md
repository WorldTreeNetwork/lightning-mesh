## Comparison and steelman

The amended contract resolves most of the original ambiguity. `open_app_tun` is explicitly an Admin-library runner called by a test or second process; the guild snapshot computes and displays an address without starting transport. Dependency injection of one labeled connection is sufficient for this increment. The peer address, node id, exact host route, unknown-peer rejection, MTU 1280, partial-setup rollback, explicit task abort on drop, and Linux/non-Linux behavior are now stated. No QUIC handshake, automatic desktop activation, foreign /48 routing, or authenticated peer discovery is needed to accept this seam-only contract. A supplied node label remains distinct from authenticated remote identity.

The strongest reading in the author's favor is that “workplace” in the design was intended to mean a nested guild, and that the caller would drop a session when either encap task exits. Both would produce a reasonable implementation. Neither is what the current contract unambiguously says: the existing workplace is a house, and the caller's disconnect responsibility is not specified. These are residual obligations from r1, not a competing design.

## Status of the three original owed items

1. **Inputs and executable path: substantially answered, with one selection contradiction.** `design.md:9` and the delta pin the runner and supplied connection path. The delta at `specs/admin-app-tun/spec.md:5` selects the existing guild when it has no outer guild. However, `design.md:19` says “A workplace or access guild is not a house prefix.” The ceremony creates both Admin and workplace guilds with profile `house` (`admin/src-tauri/src/guild_ceremony.rs:234`), and the panel preferentially selects the workplace (`admin/src/lib/guild/mock/GuildPanel.svelte:44`). Following the delta displays the workplace-derived app address; following the design suppresses it. Reconcile the rule and add a selected-workplace-house versus nested-access acceptance case. The existing selected top-level house rule is sufficient; no new selector is requested.

2. **Lifecycle and status: partially answered.** `design.md:11` and the delta at line 7 now assign ownership and rollback on partial setup, drop, and guild/key change. They still do not specify what triggers teardown when the connection closes or either encap task terminates, or how `up` changes then. In `spawn_encap_pair`, receive-side closure returns from `rx` while `tx` may remain blocked on a TUN read; there is no paired cancellation or session-drop notification built into that function. Dropping the owner is sufficient cleanup only if someone is obliged to do it. Pin either session supervision or an explicit caller obligation that observes completion, stops the sibling task, removes owned network state, and reports the computed address with `up=false`. Also make the startup `up=true` condition concrete: usable assigned /128, installed peer route, and running seam, without treating this as proof of remote reachability. The spike's `nodad` setup does not define the product's address-usability policy. Add the previously owed focused acceptance for partial route-setup failure, connection/task termination while idle, and guild/key removal or replacement. The existing generic “test … one packet across the seam” task does not cover these failures.

3. **Discriminating spike evidence: answered for the stated seam.** The new source derives both fixture addresses, moves each TUN into a different netns, installs the peer host routes before the seam-off ping, observes IPv6 ICMP request/reply packets with the expected destinations on the paired connection endpoints, and checks failure after abort. `evidence-r2.log` records off=false, on=true, request=2, reply=2, other=0, abort=false, exit 0. Separate namespaces and both negative controls rule out the original same-netns local-delivery explanation. The count of two can include the queued seam-off request and is not proof of exactly-once delivery; the contract does not require that. The unattached third label is a useful scope check, not evidence of production peer selection or authentication; the unknown-peer product scenario remains necessary. The finding's “Minimal Test” paragraph still describes the first fixture, but its Evidence section clearly supersedes that run. This stale paragraph does not invalidate the new evidence. `Unverified hypotheses: None` is supportable for seam traversal, not a claim that lifecycle behavior has been verified.
