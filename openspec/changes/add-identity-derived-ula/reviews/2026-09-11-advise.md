## Blind take (written before opening design.md / tasks.md)

Inputs: proposal Why/What, `openspec/specs/link-local-mgmt/spec.md`,
`ipv6-addressing-decision.md`, `ipv6-parallel-plane.md`, `tun/link.rs`
(`backhaul_addr`, `BACKHAUL_PREFIX_LEN` comment), `tun/iface.rs`
(`overlay_link_local`), `mjolnir-meshd.rs` (`DirectoryNode`,
`assign_backhaul_addr`, `reconcile_backhaul_addr`), `babel/config.rs`
(`render_overlay_babeld_conf` deny lines).

1. PIN the derivation as a pure function in `tun/link.rs` beside
   `backhaul_addr`, byte-exact in the ADR, with a golden vector test. Three
   implementers (meshd, Admin, a future app) must agree without talking.
2. PIN what the /48 global id hashes. There is no "mesh identity" in the code
   today (no mesh secret, no mesh id string; only UCI 802.11s `mesh_id`/SAE).
   Either name the exact input string or use a fixed constant /48 (hash of
   `"mjolnir-mesh"`). Refuse a per-box random /48 — that is the OpenWrt prefix
   we already filter.
3. PIN on-link semantics. Address = /48 + subnet-id 0 + 64-bit IID from
   `blake3(node_id)`. Assign it on `br-mesh` with prefix length **/64**, so all
   nodes share one /64 and are on-link (SSH-to-ULA works). A /128 per node, or a
   /64 per node, makes peers off-link and the user journey false.
4. PIN the IID clamps, mirroring `backhaul_addr`'s `.0.0`/`.255.255` avoidance:
   never IID 0 (subnet-router anycast), never the RFC 2526 reserved anycast
   range (`…:fdff:ffff:ffff:ff80/121`). Cite RFC 7136 (IID bits are opaque; no
   u/l bit games).
5. PIN DAD + reconcile. `link.rs` records that binding a ULA "trips IPv6 DAD"
   for iroh; the design must say whether the address is added `nodad` or DAD is
   allowed (1 s tentative). Either way netifd wifi reload flushes `br-mesh`
   addresses, so the ULA needs the same `reconcile_backhaul_addr` treatment.
6. PIN babel containment with a test. `redistribute local deny` + `redistribute
   deny` are family-agnostic, but the `in`/`out` deny lines are v4-only. Add
   `in ip <ula>/48 deny` / `out ip <ula>/48 deny` to both renders (br-mesh and
   `mjolnir0`) and assert them, so v6.4 has to opt in deliberately.
7. PIN the "not an iroh candidate" guarantee. Today it holds only because iroh
   1.0 does not surface ULAs (a version quirk). The design must state whether
   it relies on that passively or filters explicitly, and add a post-deploy
   check that no peer candidate starts with `fd`.
8. REFUSE any coupling of the ULA to the IPv4 backhaul host16. `pt9` can
   re-derive `10.254.x` after a claim loss; the ULA must hash `node_id` alone
   so it never moves. Refuse touching `overlay_link_local`, `pt9`, or `10.254`.
9. REFUSE `mjolnir0` assignment in this change unless the deny lines land
   with it. Nothing routes v6 over the TUN before v6.4; putting a ULA on
   babeld's tunnel interface is exactly the `buw.1` "local address poisons the
   path" shape. `br-mesh` only is the safe v6.2.
10. TRADEOFF: fixed well-known /48 vs per-mesh /48. Fixed is the only way the
    user journey ("computable from the node id without asking anyone") is
    literally true, and it is what a `.mesh` AAAA stub (v6.5) can compute
    offline. Per-mesh /48 buys federation (`yau`) separate planes at the cost of
    a second input. I would take the constant now and let `yau` revisit.

## Compare (after design.md, tasks.md, delta spec)

Steelman first: the design answers the hard half of the take well.

- Take 1 (pure fn beside `backhaul_addr`) — tasks box 1. Answered.
- Take 2 (what the /48 hashes) — design names it: `blake3(mesh_id)`, where
  `mesh_id` is the CRDT gossip topic. Answered in principle; see S1 below.
- Take 3 (on-link semantics) — design picks `/128` host, assigned as `/64`
  on the iface, explicitly so the node is the subnet router for `v6.3`.
  Answered, and better argued than my take.
- Take 4 (IID clamps) — "u/l bits left as hash output" covers RFC 7136. IID
  0 / RFC 2526 anycast are 2^-64 / 2^-57 events; a clamp is parity with
  `backhaul_addr`, not a blocker. Note only.
- Take 8 (never couple to the v4 host16) — IID is `blake3(node_id)`. Answered.
- Take 10 (fixed vs per-mesh /48) — design chose per-mesh, but today
  `mesh_topic_id()` is a compiled constant, so the /48 is a constant in
  practice. The tradeoff is deferred, not lost. Fine.

What the author has not answered. These are the send-back items.

### S1 — `mesh_id` input is a protocol-version string, and the bytes are ambiguous

`mjolnir-meshd.rs:682` `mesh_topic_id()` is `blake3(b"mjolnir/mesh/crdt/v0")`,
private to the bin. "PSK-derived when membership exists" is not in the code.
Two problems:

- The ULA `/48` is tied to the CRDT topic tag. Bumping the topic to `v1` for
  any gossip reason renumbers every node's ULA fleet-wide, silently. The /48
  input must be its own domain-separated constant (e.g. `mjolnir/mesh/ula/v0`)
  or a real mesh identity, never the wire-protocol topic.
- "first 40 bits of `blake3(mesh_id)`" — is `mesh_id` the ASCII string or the
  32-byte `TopicId` (already a blake3)? Admin and a future app must produce the
  same bytes without reading meshd. The ADR task must state the exact input
  bytes and ship a golden vector.

### S2 — `/64` on `mjolnir0` black-holes on-link ULA traffic (design defect)

Design: "Also on `mjolnir0` when the overlay TUN is up … assign as `/64` on
the iface." That installs the same connected `fdxx::/64` on `br-mesh` and
`mjolnir0`. The kernel then has two on-link routes for every peer's ULA and
picks one by metric/insertion order, which is not stable across reboots or
wifi reloads. When it picks `mjolnir0`: `tun/overlay.rs` production demux
routes unicast by `LPM(dest) -> next-hop` over the v4 table and drops
unroutable unicast; there is no v6 FIB before `v6.4`. Result: `ssh <peer
ula>` on the same island intermittently black-holes, which falsifies the one
user journey in the proposal ("SSH to that ULA works on-link once assigned").

Fix (author's call, pin one):
- (recommended) `br-mesh` only in this change. `v6.4` owns the TUN, and
  "without a new assign path" is not a real saving: the assign call is one
  netlink line.
- or assign `/128` on `mjolnir0` (no connected route), never `/64`.

Not the `buw.1` poisoning shape I feared in the blind take: `redistribute
local deny` is family-agnostic, so babel will not export it. The defect is
kernel connected-route ambiguity, not babel.

### S3 — no reconcile after wifi reload

`reconcile_backhaul_addr` (`mjolnir-meshd.rs:6753`) re-adds the v4 backhaul
because netifd flushes `br-mesh` addresses on wifi reload. It is v4-only
(`IpAddr::V4` throughout). The `v6.1` link-local did not need this because the
kernel regenerates `fe80` itself; a manually added ULA does not come back.
Tasks box 2 ("Assign on `br-mesh`") must include the reconcile, or the ULA
disappears at the first `wifi reload` and `/api/node` goes stale (it will
still print the address the daemon assigned, not what the kernel has).

Also pin DAD: `rtnetlink` `address().add` runs DAD (1 s tentative) unless the
`nodad` flag is set. Say which. With a 64-bit hashed IID, `nodad` is
defensible and avoids the tentative window the `link.rs` comment warns about.

### S4 — babel containment is asserted nowhere

Proposal: "Do not export it in babel IPv6", "Stock OpenWrt `ula_prefix` stays
filtered". Design and delta spec have no requirement or scenario for either.
Today containment holds by `redistribute local deny` (family-agnostic), and
the `in`/`out` deny lines in `render_overlay_babeld_conf` are v4-only. Owed:
one scenario in the delta spec, and `in ip fc00::/7 deny` / `out ip fc00::/7
deny` in both renders with a test, so `v6.4` opts in by editing a line rather
than discovering that nothing ever stopped it. `fc00::/7` also covers the
stock random `ula_prefix` regardless of what `mesh_id` resolves to.

### S5 — "test or comment guard" is not a guarantee

Tasks box 4 lets a comment stand in for the iroh non-candidate property. A
unit test cannot observe iroh's candidate discovery, and a comment does not
survive an iroh upgrade that starts surfacing ULAs. Owed: a runtime
observable (log or `/api/node` field listing iroh local candidates) and a
fleet health-gate assertion that no candidate is in `fc00::/7`. The delta
spec scenario "iroh lists connection candidates … the ULA is not" already
implies this; make the task match the spec.

### Notes (body, not verdict)

- The delta spec has no scenario for on-link SSH, which is the only user
  journey. Add one under "ULA sits beside 10.254".
- Pre-`v6.4`, cross-site nodes' ULAs look on-link on `br-mesh` but are not
  reachable. State that in the ADR so nobody files it as a bug.
- Spec says "SHALL NOT add that ULA to iroh's … bind set". iroh binds
  wildcard `[::]`, which implicitly includes it. The memory's finding was
  about binding the ULA *directly*. Reword to "candidate set / direct bind".
- `mesh_topic_id` is private to the bin; the pure `ula_addr(mesh_id, node_id)`
  in `tun/link.rs` needs the input passed in, so move the constant to the lib.
