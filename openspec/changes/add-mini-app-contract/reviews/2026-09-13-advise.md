## Independent take — blind pass

1. Pin `app=v1` to the existing TXT map and to HTTP(S) services; no CRDT schema or reserved-name change belongs here.
2. Pin one canonical entry URL from the advertised service origin plus a strictly relative, normalized `path`; neither TXT nor manifest may redirect execution to another origin.
3. Refuse every embed whose computed child origin equals the current `hello.mesh` or gateway-IP page origin, including raw-IP fallback and default-port equivalence.
4. Pin tap-to-load: manifest discovery may decorate an inert card, but no app document, script, cookie, or storage is touched before an explicit visitor action.
5. Pin a sandbox that grants only capabilities the contract names; if the bridge needs the child’s real origin, `allow-same-origin` is tolerable only behind the hard cross-origin refusal in line 3.
6. Pin both bridge directions to an exact computed origin and the expected `WindowProxy`; refuse `*`, `null`, source-only checks, origin learned from a message, and origin supplied by the manifest.
7. Pin a discriminated, versioned envelope with strict field validation, bounded serialized bytes, unknown-type rejection, and no identity-bearing message in v1.
8. Treat every manifest value as untrusted presentation data: bounded fetch/body, schema allowlist, plain-text rendering, constrained URLs, and no HTML, CSS, or executable URL sinks.
9. Pin link-out as the universal fallback for CORS, timeout, malformed/oversize manifest, unsupported version, refused origin, blocked frame, and bridge failure.
10. Tradeoff: retaining a real cross-origin app origin enables storage and exact `postMessage` pinning, but it demands a stronger pre-frame origin proof than an opaque-origin sandbox would.

The ten lines above were written before opening this change's `design.md`, `tasks.md`, or delta spec.

## Comparison and steelman

The proposed design answers most of the blind-pass concerns directly. It keeps the marker in existing TXT, limits apps to HTTP(S), validates a relative entry path, makes the manifest presentational, loads frames only on a tap, preserves the app's own origin, specifies a capability-limited sandbox, checks both message source and exact origin, pins outbound `targetOrigin`, rejects unknown bridge types, and retains link-out everywhere. The strongest case for the chosen design is the deliberate pairing of `allow-same-origin` with a cross-origin precondition: it gives an app normal storage and a non-opaque `event.origin`, making the exact-origin bridge possible without putting app code in the parent document.

That pairing also makes the precondition security-critical, and the current protected-origin set is incomplete. The delta says “every hello.mesh origin” but defines that as only the current page origin plus `http://hello.mesh`. The cited deployment surface serves the SPA separately at each node's `http://10.42.<x>.1`, and those gateway origins can each hold a rung-1 key. Meanwhile the cited entry-URL rule uses the record IP for dotted mDNS-style names. Thus a page at `http://hello.mesh` can regard `http://10.42.7.1` as cross-origin and frame it, even though app-controlled code at that URL executes in a gateway origin that may hold the visitor's key. With `allow-scripts allow-same-origin`, that is exactly the boundary the change says it protects. The contract must derive or conservatively recognize all key-bearing gateway origins and fall back to link-out for them; checking only the current origin is insufficient.

A robust rule is to compare the canonical entry origin against `http://hello.mesh`, the current origin, and every node LAN-gateway origin derivable from the directory snapshot. If the implementation cannot enumerate that set completely, it should conservatively refuse raw gateway-IP HTTP origins at the hello service port. The tests need the cross-history case: parent at `http://hello.mesh`, key previously stored under `http://10.42.7.1`, and an app record whose entry resolves to the latter.

Two smaller contract ambiguities should be resolved while amending:

- Manifest discovery itself contacts every app host even if the iframe does not load. That contradicts the design rationale that tap-to-load avoids announcing the visitor to every app host. Either defer the manifest fetch until visitor intent or explicitly accept that disclosure and narrow the claim; add a scenario that makes the timing observable.
- Define the 16 KiB cap as UTF-8 bytes of successful JSON serialization, with serialization errors rejected rather than thrown. Require `resize.height` to be a finite number before clamping. Otherwise cyclic structured-clone data, `BigInt`, `NaN`, and infinities leave implementations and tests under-specified.

The manifest's execution authority is otherwise appropriately constrained: it does not select the entry origin, and its fields are limited to text or an image source. URL construction should still finish by asserting that the canonical entry URL's origin equals the advertised entry origin, so path validation is defense in depth rather than the only origin guard.

## Flagged questions

Do not require the service-record owner to be a known fleet node in v1. `DirectoryService` does not currently expose `owner_node_id`, “known fleet node” is not a trust claim about app code, and such a gate would quietly replace decentralized publication with fleet admission. Origin isolation is the correct rung-1 boundary. A later trust/provenance change can expose and label the owner without conflating publication with endorsement.

The 16 KiB bridge cap is ample for the four tiny v1 messages and is sane once byte measurement and failure behavior are specified. The 120–640 CSS-pixel clamp is also sane for an embedded card; reject non-finite/non-number input, clamp both manifest and bridge heights through one function, and retain link-out for experiences that need more room.

## Verdict

Send back for the incomplete key-bearing-origin refusal. The overall architecture is coherent and should pass after that boundary is closed and the two observable protocol ambiguities above are pinned. No product code, fold, or banner change is warranted in this pass.
