# Fresh architecture advise r2 — add-household-owner-claim

> **ADVISE:** send-back

> **SPAWN:** .spawns/mjolnir-mesh-bf7.1-1792654293-88966-d89399ac

Scope: contract and design acceptance at HEAD `d3e71fb`, against the r1
send-back's R1–R4 (`reviews/2026-10-22-advise.md`). Nothing here claims built
behavior. Settled decisions are not reopened: the method needs both factors,
the window is 120 s, the profile lifetimes stand, there is no TPM or factory
attestation, and no custom key exchange.

## Blind pass (written from the proposal, the household-authority delta, and cited code, before reopening design.md / tasks.md / spec delta)

1. **Pin** a card secret that is off-device, high-entropy and one-time. The node keeps only a verifier and never displays the secret.
2. **Pin** that the secret never crosses plaintext :80 in a reusable form. The proof binds the owner pubkey, node id, epoch and a node-issued nonce, with standard HMAC/HKDF only.
3. **Pin** that the verifier the node stores is the key the node can actually check the proof against. Say what a flash read gives an attacker.
4. **Pin** whose code holds the secret. On an open AP, code that the entry router serves can be swapped by a rogue AP. So card entry belongs in the installed app, not in the hello.mesh page.
5. **Pin** that the client checks the device signature against the card's node id before it sends anything derived from the secret. The node's own signature is not an acceptance factor.
6. **Pin** how a press is dispatched against `rc.wps/00-mjolnir-wan-admin`, for each of three node states: unclaimed with a verifier, no verifier (developer fleet or post-reset), and owned.
7. **Pin** a single durable CAS winner in meshd. A local record decides; gossip does not.
8. **Pin** what recovery does: both epochs advance, recovery creds are retired, and a node holding a forked head fails closed for privileged ops while forwarding stays up.
9. **Refuse**: button-only, secret-only, WPS as presence, hub holding the owner key or the raw secret, and a reset that re-arms the old card.
10. **Tradeoff**: the attempt cap stops online guessing, but an on-path attacker can burn the attempts and close the window. That is acceptable as DoS-only, provided it is stated.

## Compare

**R1: answered.** The card is off-device, and the node "never displays it,
including after reset". Reset clears the binding and the verifier, does not
re-arm the card, and leaves the node unclaimed until a provisioning image
writes a new verifier. The node id is unchanged. That picks one side of the
r1 tradeoff and states it. The spec delta matches.

**R3: answered.** The client verifies the node signature against the card's
node id before it sends anything derived from the secret, and "The node does
not treat its own signature as an acceptance factor." The spec delta puts the
check on the client. Residual wording is non-blocking (N1).

**R4: answered for two of three states.** Unclaimed or pending-recovery arms
the ceremony only. Every other state toggles WAN SSH. The rc.wps hook only
signals meshd, and meshd owns the window and the CAS. See B3 for the third
state.

**R2: the shape is right, but the pin doesn't work as written.** The raw secret
stays on the client. The MAC binds owner pk, node id, epoch and nonce. The
entropy is ≥ 80 bits, the cap is 5 attempts per window, the nonce is fresh per
attempt, hello relays with a 5 s timeout, and the delta reads "raw provisioning
secret". All good. Two gaps remain, and both sit inside R2's own threat
(sniffing or rogue AP on the open client AP):

### B1: the stored verifier cannot verify the proof (blocking)

design.md says the node stores `HMAC-SHA256(node-local salt, secret)`, and the
client sends `HMAC-SHA256(secret, owner pk ‖ node id ‖ epoch ‖ nonce)`. meshd
cannot compute a MAC keyed by the raw secret from a one-way hash of the
secret, so the comparison it is said to run is impossible. An implementer has
to pick between storing the raw secret and changing the key.

Steelman: either fix is secure, so this is just an editing slip. True, but R2
asked for exactly this pin, and the slip also hides a property worth stating.
With any symmetric MAC, the stored value is key-equivalent: whoever reads it
can forge proofs, though they don't learn the card string.

**Required pin:** `k = HMAC-SHA256(salt, secret)`. The salt is either printed on
the card or carried in the node-signed challenge. The node stores `k`, and the
proof is `HMAC-SHA256(k, owner pk ‖ node id ‖ epoch ‖ nonce)`, with the nonce
issued by the node in the signed challenge. State that `k` is secret-equivalent
for forging and that reading flash counts as physical compromise. Reset
already wipes it.

### B2: name the claim client, and keep it off the hub origin (blocking)

The r1 send-back allowed "Lightning Admin or hub JS" as the verifying client.
On the shipped network that option does not hold. Suppose the client is
JavaScript served by hello over plaintext HTTP on the open AP (or by a rogue
AP with the same SSID). Then the attacker serves JS that skips the node-id
check and posts the typed secret to itself. The purchaser presses the button,
and the attacker's own-key claim is the first complete one. The design's
"raw secret never leaves the client" holds only when the client's code does
not come from the network under attack.

The design never says which client, and the delta scenario "Claim from the hub
origin" suggests the hub page is one. The umbrella already answers this. Its
household-trust-contract proposal says the purchaser claims "in the installed
app", so this is alignment, not new scope.

**Required pin:** card secret entry, owner keygen and the HMAC run only in an
installed client whose code is not served by the node (Lightning Admin). The
hello.mesh page may point the purchaser to the app. It never accepts the card
secret. Change that delta scenario to "hub handlers never receive the card
secret, and the hub page offers no secret entry."

### B3: button dispatch for a node with no verifier (blocking, wording)

The design says reset leaves the node "unclaimed until a provisioning image
writes a new verifier", and that cardless fleet nodes "stay developer-owned".
The dispatch rule sends "unclaimed" presses to the ceremony. If a node with no
verifier counts as unclaimed, every current fleet node and every reset node
loses the WAN-SSH toggle. That toggle is today's in-band WAN-side access, and
the press would arm a ceremony that can never complete.

**Required pin:** the dispatch has three states. With a verifier present and
unclaimed, or with a pending recovery, the press arms the ceremony. With no
verifier (developer-owned, or post-reset with no image), the press keeps the
existing WAN-SSH toggle. On an owned node, the press toggles WAN SSH. Add one
test line covering the no-verifier case.

### Non-blocking

- **N1.** design.md still opens with "every required factor verifies" and lists
  device proof as factor 1. Reword it as two node-side factors (proof and
  button) plus one client-side check, to match the later paragraph and the
  delta.
- **N2.** Count a "pending recovery request" toward dispatch only after its
  recovery credential has verified. Otherwise anyone remote can suppress the
  owner's WAN-SSH toggle by posting a pending request.
- **N3.** Pin how the card encodes the node id: the full ed25519 key, or a
  fingerprint of at least 128 bits. With a short fingerprint, a hostile entry
  router can grind a key whose fingerprint matches.
- **N4.** State that an on-path attacker can spend the five attempts and close
  the window. That is DoS only, and the purchaser presses again.
- **N5.** Name which button or action performs the destructive "local reset".
  KEY_RESTART is a separate button per the rc.wps hook comment. Also state that
  the house sees the node as lost and not recovered.

## Verdict

**Send-back.** R1 and R3 are answered. R4 is answered except for the
no-verifier state (B3). R2 has the right construction, but its stored-verifier
pin can't run as written (B1). Its threat model also isn't closed until the
claim client is pinned off the hub origin (B2). All three fixes are one or two
sentences in design.md and the spec delta, plus a test line. None of them
reopens a settled decision.
